# 语言画像原话初版与回复关系来源审查

记录日期：2026-10-27。前半为当前源码实现，后半仅为来源审查与建议，不表示回复分析已经交付。
本轮未连接真实账号、未读取真实聊天数据库，测试和页面样例均为人工构造。

## 1. 本轮改动及审核入口

### 语言画像

- 保留章节原有纵向模块顺序、成员卡片和字体，直接减少模块间距与固定留白。
  私聊原有双方并列卡片保留；共同词、偏好词继续上下排列。
- 成员常用词、群聊特色词与“常聊”词、私聊共同词和偏好词均可点开原话。
  默认不展开，悬停不弹窗；词上不增加数量角标或常驻下划线。
- 点击后打开只读原话面板，显示发送者、时间、完整的用户撰写文字。
  默认按导入顺序展示三条匹配消息；“查看全部原话”进入十条一批的列表，继续查看可到最后一条。
- 每条匹配可单独展开“前后几句”：前后各最多两条、距离命中消息不超过十分钟。
  这是一小段可选择的邻近上下文，不代表复原整轮聊天，也不是引用回复链。
- 关闭面板恢复原词的焦点与阅读位置，原文可选中、复制，HTML、脚本和链接按普通文字显示。
- 2026-10-27 验收修正：展开／收起以段落起点保持可见，不再固定下方按钮而把前文推走。
  面板打开期间锁定底层报告滚动并保留滚动条占位，短列表、标题处和滚动边界均不穿透；关闭后恢复正常滚动，打印不受屏幕滚动锁影响。
- 点击面板外的遮罩可以关闭；面板内空白和从原文拖选到面板外均保持打开。
  报告交互控件统一移除浏览器默认焦点黑框，键盘保留细线提示，鼠标操作不遗留突兀边框。
- 微信原话中的 `wxid:\n` 问题已定位为群消息存储头部残留，发送者昵称映射正常。
  在微信文本适配时，仅对确认的群聊非本人消息移除与该行发送者完全匹配的一层头部；正文换行／空格保留，私聊、未知会话、本人文字与不匹配前缀保留。
  处理发生在过滤和分析前，避免存储字段影响质量过滤、长度及表达邻近词；不是在原话界面全局删除账号文本。

### 表达文化与表情包

- 表达文化顶部概览、最常用表达、伴随词组合维持纵向排列，只收紧间距。
  仅最后的成员表达区在宽屏排成两列，窄屏回到一列，打印时取消滚动裁切。
- 表情包只保留负责人已要求的“使用风格”右侧“约 XX 种”字号缩小；没有调整特色算法或章节组织。
- 表达文化在展示选择后移除没有可展示项的成员，不再留下姓名与空白。只使用自定义表情包或表达未达到已有重复展示门槛的成员也可能属于这种情况；分析层成员及总量不因此改变。全部成员均无展示项时隐藏该章节。
- 第二章特别聊天的原文回忆卡继续暂停，留待 0.4.0，不借此次词语原话入口实施。

### 验收追加：整句重复噪声

原噪声检测只尝试最长十二字的重复片段，而长文本规则从一百字开始，导致十几字的句子连续复制后仍不足一百字时漏过两条规则。
修复去掉重复单元长度上限，保持整条文本精确重复至少三遍、总长至少八字的既有条件；两遍强调、重复句后含不同补充正文保持保守保留。
该规则仍在共用质量过滤层按整条消息排除，QQ／微信使用同一链路，词频和原话关联都消费过滤后输入；不改写原始消息，也不在页面隐藏已计入词频的文字。
虚构样本先复现漏滤及 QQ／微信导出词频增加，再验证修复；表达文化空成员也按展示投影到实际导出验证。当前分析修订为 `echo-analysis.v12`。

### 群聊成员浏览

负责人追加确认成员排序与查找：交流节奏、语言画像、表达文化默认按发言量，可选昵称、最早出现，表达文化另有表达次数；私聊保持原样。
最早出现的序号来自过滤后输入，在既有发言量排序前保存；不从不完整的原话表反推。昵称、备注与群名片查找仅重排／隐藏已有展示节点，保留原话下标和当前节奏对象；没有匹配时显示简短提示。
共用前端位于 [echo_member_controls.py](../src/qq_chat_analyzer/presentation/echo_member_controls.py)，不新增缓存、持久化设置或后台检索。加入此展示信息后的 schema 为 `echo-report.v0.13`、分析修订为 `echo-analysis.v13`。

## 2. 原话关联的口径与保存边界

实现链路：保留消息 → 原有清理与分词 → 选出展示词 → 关联该成员的实际 token → 共用原文表 → 离线 HTML / JSON。
主要代码为 [analysis_service.py](../src/qq_chat_analyzer/application/analysis_service.py)、
[language_sources.py](../src/qq_chat_analyzer/presentation/language_sources.py)、
[echo_language.py](../src/qq_chat_analyzer/presentation/echo_language.py)。

| 项目 | 初版行为 |
| --- | --- |
| 成员范围 | 按稳定发送者键绑定画像成员；共同词与偏好词可查看双方原话。原话中同名成员用报告序号区分，不额外暴露来源 ID。 |
| 匹配依据 | 直接复用此次分析的每条消息词法 token；不重新分词，也不使用子串匹配。`apple` 不命中 `pineapple`。 |
| 计数 | 同条消息两次命中计两次出现、一个原话条目；面板明确区分出现次数与消息数。 |
| 过滤范围 | 只关联时间范围、发送者排除、模板排除与质量过滤后的保留消息；上下文也不能越过导入位置中被过滤掉的记录。 |
| 上下文停止 | 平台、会话、类型不一致，缺少会话身份、时间未知／逆序、非相邻导入位置或超过十分钟时停止；无可靠上下文仍展示命中原话。 |
| 顺序与缺口 | 保留实际导入顺序；不把来源缺失、查询前已略过的不支持类型伪装成完整原生聊天。不会保证前后两条就是客户端中的前后两条。 |
| 原貌边界 | 保存 `ChatMessage.text` 的原有用户撰写投影，不保存分词后的拼接句，不改写、不伪造高亮；不能由此重建完整富媒体、引用快照或 QQ 结构化提及名称。 |
| 去重与 ID | 同一保留消息在原文表中保存一次，各词引用报告内部序号；重复或缺失来源 message_id 不会把不同消息合并。 |
| 完整列表 | 对展示词保存全部匹配，初版不随机换样、不暗中截断。分页只减少 DOM 工作量，不减少文件字节数。 |
| 离线与生命周期 | 不新增数据库访问、网络请求、额外缓存或目录；原话存入现有报告包的 HTML 与 JSON，沿用报告包删除与保留机制。分享文件时原话一起分享。 |
| 版本 | 新报告 schema 为 `echo-report.v0.12`；原话初版的展示改动不修改分析修订，后续微信群文本存储头部修正为 `echo-analysis.v11`，整句重复噪声修正为 `echo-analysis.v12`。已有报告不回填或改写，需重新生成。 |

只索引展示词并不保证文件永远很小：当词覆盖大量消息，上下文与命中表可能接近整个保留范围。
本轮给出虚构数据测量，不能据此保证所有超大群或旧设备的内存与响应速度；不要把分页称为压缩。
不支持原话的旧报告保持原有静态阅读方式。

### 本机虚构压力样本

人工构造一个展示词命中每条消息、正文约三十字的输入；计时启用 tracemalloc。
这是原话关联与浏览器分页的测量，不是完整分词、分析、序列化或整机峰值内存基准，也不含大群大量展示词的最坏情况。

| 消息数／全部命中 | 原话关联耗时 | 关联阶段额外峰值分配 | 原文表 JSON | 完整 HTML |
| --- | --- | --- | --- | --- |
| 10,000 | 0.942 秒 | 6.60 MiB | 2,512,316 字节 | 4,618,335 字节 |
| 100,000 | 10.778 秒 | 65.05 MiB | 25,822,314 字节 | 26,398,333 字节 |

隔离 Edge 中，两份文件都只先渲染三条，进入全部时渲染十条；导航至页面可用约 137 / 610 毫秒，
点击与首批十条创建约 5.5 / 2.1 毫秒。单次本机测量仅用于确认初版没有把十万条直接铺进 DOM，不能用于对外承诺性能。

## 3. 回复关系：当前真正能拿到什么

审查覆盖 Provider → Adapter → RichMessage → Import → 过滤 → 现有消费者，不以消息类型标签代替目标关联。

| 来源 | 当前拿到的事实 | 目标消息关联 | 能力边界 |
| --- | --- | --- | --- |
| QQ 群数据库 | 消息 ID、会话、发送者、时间、正文；可选原生序号 `40003`，引用段 `45002=7` / `47402` | 同一查询会话内，引用序号唯一对应一条目标记录时生成 `ReplyRelation(target_message_id)` | 目标不在查询窗口、缺序号、重复序号或会话不匹配时不生成目标关系。后续消费者还必须检查目标 ID 唯一性、过滤范围与时间顺序。 |
| QQ 私聊数据库 | 能识别引用段、保留当前发言，类型可为 `reply` | 当前没有可靠映射；Provider 私聊查询未取群序号，Adapter 也不套用群聊索引 | 不能以 `reply` 类型或 @ 人名推定“回复了谁”。私聊字段与命名空间需另行验证。 |
| 微信官方数据库 | 低 32 位类型 1 的文本与 47 的表情包；时间、发送者、会话及来源 ID | 当前不产生 ReplyRelation | 查询条件仅支持 1 / 47，应用消息／引用承载类型尚未接入；引用消息可能在读取入口已被排除，不能统计为“没有人引用”。 |
| 微信 CLI 导入 | `reply` / `quote` / “引用消息”等字符串类型映射为带文本消息 | 没有目标 ID 关系 | 只有类型标签；上游已扁平化的文本也不能可靠反推出引用目标。不是官方数据库路径的补救读取通道。 |
| ChatLab 等普通导入 | 某些格式能标记 reply 类型，保留各自支持的文字 | 当前无通用可靠目标关系 | 不能从类型 25 或普通文本构造精确回复边。未新增数据源或恢复退休入口。 |

### QQ 群链路的关键事实

- [qq_database_provider.py](../src/qq_chat_analyzer/providers/qq_database_provider.py)：群查询在字段存在时选择 `40003`，旧 schema 不凭空填充；私聊使用自己的会话查询。
- [qq_db_adapter.py](../src/qq_chat_analyzer/qq_db_adapter.py)：只为群会话建立序号索引；引用段解析到 `47402`，只有唯一目标才生成关系。引用附带的不透明内容不并入作者当前正文。
- [rich_message.py](../src/qq_chat_analyzer/rich_message.py)：ReplyRelation 目前只有目标消息 ID，没有原生线程、完整引用快照或多层对话树。
- [import_service.py](../src/qq_chat_analyzer/application/import_service.py) 保留 Rich 与投影实例的配对；应用层过滤同步排除 Rich 事实。
- [group_stickers.py](../src/qq_chat_analyzer/analysis/group_stickers.py) 的 `_replies()` 已消费这类关系，但只服务“明确引用附图”：要求来源 QQ、双方身份可靠、唯一目标、不同作者、顺序可靠且引用方含可辨认表情包。它不是通用回复网络。

### 微信的真实缺口

[wechat_database_provider.py](../src/qq_chat_analyzer/providers/wechat_database_provider.py) 的正文与时间边界查询均限定 `(local_type & 0xFFFFFFFF) IN (1, 47)`；
[wechat_db_adapter.py](../src/qq_chat_analyzer/wechat_db_adapter.py) 只接受对应两类，并未构造 ReplyRelation。

后续需针对应用消息／引用承载记录做受限调查：确认实际 local_type / 子类型、正文编码、引用目标字段及其命名空间，
再判断是否可用 server_id 对接原消息。当前尚未验证这些字段，不能把“通常用类型 49 / 某 XML 字段”写成 Echo 已支持或跨版本稳定合同。
缺失 server_id 时的 local_id 也未证明能跨 shard 唯一，不能裸用来连边。
若引入新类型，必须同步审查消息起止查询、统计数量与分析修订，并把作者当前文本和引用附带原文分开。

## 4. 已确认的产品边界与后续候选

负责人于 2026-10-27 确认：回复关系分析是群聊专属功能。私聊相关信息仅作为“交流的节奏”的小补充，
不设对称的回复关系章节、关系图或排行榜。后续功能按场景价值设计，不再要求私聊、群聊机械对标。
具体私聊补充项尚未确定；拍一拍／戳一戳仍是待验证的数据与产品候选，不因本次边界确认自动进入实施。
本节确认的是产品范围，尚未授权开始回复关系功能实现；上节私聊来源缺口保留为审查事实，不作为群聊功能的前置任务。

1. **QQ 群先做明确引用的只读列表或简要统计**。复用 RichMessage，不从相邻发言猜回复；只纳入当前保留范围内、目标唯一且身份／顺序可信的关系。保留无法定位的数量，称为“可定位的明确引用”，不宣称完整互动网络。
2. **微信群先验证来源字段**。核实引用承载类型、正文与目标键，补虚构字段样本及重复 ID／分片／范围外目标测试，再进入统计设计。QQ 私聊的目标映射不列为本功能待补齐项。
3. **确定群聊报告中的展示位置**。可以考虑“谁常明确引用谁”“被引用的原话”，或给群聊原话面板增加可靠的被引用上下文；这些是后续候选，不在此次初版实施。私聊只按需要完善已有交流节奏。

不推荐现在做“回复率”“忽略率”或关系强弱评分：目前可见关系只是明确引用的子集，普通承接聊天并不一定引用；
不能用全部消息数当未经定义的回复率分母。现有私聊首句响应是轮次起始后的首次另一方发言，也不等于每条消息的回复耗时。
引用链可以后续讨论，但必须处理目标已过滤、未知时间、同秒顺序、环、重复键和范围外目标；不能自动加载用户已排除的原话。
