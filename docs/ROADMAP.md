# Echo Product Roadmap：0.1.0 → 1.0.0

> 状态：长期产品方向；版本主题暂定，不是实施排期、当前功能清单或验收结论。  
> 制定日期：2026-10-10；2026-10-12 根据首版发布和试用反馈调整安装、更新优先级。

## 1. 产品定位与版本目标

Echo 是隐私优先、完全本地运行的 QQ / 微信聊天分析工具：从聊天中的人物、关系、表达习惯与共同记忆出发，生成可信、好读、值得回看的数字报告。

- **0.1.0：工程底座过关。** 确保 QQ / 微信数据获取、分析、报告、隐私边界、进程生命周期与 Windows Portable 交付可靠；不要求软件形态完整。
- **1.0.0：第一个认可的完整产品。** 主要想法普遍落地，阅读与分享成熟，软件方便长期使用，新增功能不再需要反复改造基础设施；不追求完美、零 Bug 或实现所有创意。

## 2. 1.0.0 的长期目标

1. **新功能：** 相比 0.1.0，新增至少 **4–5 项面向用户的真实功能**。其中 **群聊互动关系分析、完整表情包分析**为必做。单纯新增解析字段、内部重构或重复的基础统计图不算完成新功能。
2. **结果可信：** 持续改进语言画像、智能过滤、算法正确性和可解释性，不为了有趣而给出缺乏数据依据的关系推断。
3. **数字书与分享：** 完成 Echo Report 的重大重构，压缩重复的基础章节，统一阅读、章节组织、海报、导出和分享体验；使后续新增分析容易展示和分享。
4. **完整桌面产品：** 连接稳定，历史数据受保护，具备合理的 Windows 安装方式、自动更新和失败恢复；Logo、图标、GUI、报告、海报形成一致的艺术风格。
5. **扩展成本降低：** 常规新分析功能应主要实现自身逻辑和必要测试，复用稳定的数据、分析、报告和分享通路，不必再次建设同一套基础设施。
6. **持续改善工程质量和个人能力：** 边读代码边小步清理经证实的测试、架构和实现冗余；能解释关键设计、故障处理与迭代取舍，让 Echo 成为经得起面试追问的工程作品。

**范围排除：AI 能力一律留到 2.0 再讨论，不纳入 1.x。** 不以 Star、用户数或删掉的代码/测试数量作为成功指标。

## 3. 暂定版本轮廓

| 目标版本 | 阶段主题 | 当前范围判断 |
| --- | --- | --- |
| **0.1.0** | 底层可靠与首次交付 | 2026-10-11 发布 Windows Portable ZIP（Pre-release）；跨机器兼容性与体验问题继续跟踪，不将发布等同于所有环境验收通过。 |
| **0.2.0** | 综合小修 + 安装更新验证 | 2026-10-14 已发布：首次以 Windows Setup 交付，并完成软件内发现、下载、校验、安装与重启的标准更新流程；升级与真实环境验收仍在持续收集。 |
| **0.3.0** | 第一批新功能 + 报告瘦身 | 争取 **2 项用户可感知的新功能**，压缩前段重复的基础内容；暂不全面改写电子书。 |
| **0.4.0** | 算法质量与分析结构 | 根据真实数据效果改进算法、过滤、语义和解释；不做无边界的全算法重写。 |
| **0.5.0** | 数字书式 Echo Report 与分享重构 | **一个重点阶段**：统一设计章节、阅读、海报及分享契约；允许分小阶段实施、随时保持可用。 |
| **0.6.0–0.7.0** | 第二批新功能与扩展性验证 | 再做约 **2–3 项**特色功能，通过真实接入验证开发成本是否降低。 |
| **0.8.0** | 跨版本维护与兼容收敛 | 复盘长期升级、恢复、数据与报告兼容；不重复定义 0.2.0 已经验证或交付的基础安装更新能力。 |
| **0.9.0** | 品牌与整体收敛 | Logo、图标、视觉一致性、使用文档、跨机器用户验收，原则上不启动大型新专题。 |
| **1.0.0** | 完整产品验收与发布 | 核对产品目标、功能、隐私、长期维护、发布与兼容要求。 |

**交付方式决策：** 后续以 Windows Setup 作为面向普通用户的安装入口，目标是在软件内完成发现、下载、校验、安装和重启；不计划长期并行维护 Portable ZIP 作为普通用户的交付渠道。v0.1.0 已发布的 ZIP 继续保留。0.2.0 已交付 Setup 与软件内自动更新的标准流程；后续版本沿用同一身份与仓库更新源，版本号递增。

这些版本号是**主题而非截止日期**。可以增加补丁版本、调整顺序、合并或拆分专题；不强制每个版本开发相同时间，更不为了达成版本数字堆工作量。

## 4. 新功能候选池

### 已确认必做

- **群聊互动关系：** 以可靠的关系证据分析回应、互动和成员间的交流，不用相邻消息武断推断亲密程度。
- **完整表情包分析：** 在现有 Emoji / 已支持表情基础上，完善 QQ / 微信表情包身份、使用、个人偏好与表达语义；先验证数据来源、隐私与素材许可。

### 候选，尚未承诺实施

- 引用回复关系、合并转发等聊天内容解析与用户可见分析。
- 聊天高光、历史时间轴及群聊活跃变化。
- 戳一戳 / 拍一拍等结构化互动。
- 群聊文化、趣味称号、共同表达。
- 智能过滤的人工覆盖、撤销与可解释控制。

“转发”可能指**聊天内容里的转发**，也可能指**Echo 报告对外分享**；详细设计前必须澄清，不能混同。候选功能不为凑数量强制实施。

## 5. 长期开发与学习原则

- **功能线和质量/学习线并行。** 不专设“消除 AI 味”的大版本；读到具体模块、发现实际重复与耦合，再做小范围、行为不变的重构。
- **新增能力不等于增加框架。** 保持分析核心独立于 QQ / 微信来源和 CLI / GUI；优先复用现有模型与服务，不为未验证的未来功能提前建大型插件体系。
- **用真实功能打磨接入通路。** 从一次次新增分析里提取恰当的结果、报告和分享复用能力；目标是让未来能连续、独立地开发多个功能，而非把多个功能挤进一个大 PR。
- **测试以回归价值为准。** 消除重复要先证明没有损失行为边界与历史故障覆盖，不以减少测试数量为 KPI。
- **小阶段与真实验收。** 新功能先确认范围，再 RED → GREEN → focused / 必要 Full → 真实体验；纯重构以行为保持为前提，不人为制造 RED。分离重构与功能变更提交。
- **持续掌握代码。** 围绕实际模块学习、设计、调试和复盘，留下能解释的工程证据；不能因 Echo 后续版本而无限推迟求职学习。

## 6. 记录规则与事实边界

- **本文件：** 只记录长期方向、版本主题和重大范围决策，不维护每日待办和测试快照。
- **docs/HARDENING.md：** 当前发布状态、已知限制与近期验收边界；0.1.0 上线前原始工作地图另存于 `docs/research/2026-10-10-pre-release-hardening-snapshot.md`。Roadmap 不构成已交付证明。
- **ARCHITECTURE.md / DATA_SEMANTICS.md：** 当前架构与数据语义事实来源。
- **GitHub Issue / Milestone：** 到某版本即将开始、具体事项已确认时再建立；不提前创建完整任务海。
- **每次版本完成后：** 根据真实使用反馈复盘下个版本主题，可调整本路线并简要说明原因。

> 长期成功的标志：Echo 既是一款可以放心交给别人的软件，也是开发者真正理解、能够低成本持续创造新功能的产品。
