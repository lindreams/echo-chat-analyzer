# QQ 54395 登录响应事件：定向证据与最小原型

没有继续未知地址窗口或堆扫描。

**当前判断：这是一条有明确 54395 模块依据、值得进行受控验证的事件路线；但本机真实事件与数据库认证尚未通过。**
已实现并验证自建进程的事件解析和认证原型，没有实现原生 QQ Hook，也没有运行 QScope。

## 与 NapCat 的衔接

沿用 Echo 已锁定 NapCat 4.18.34 的源码证据，详见
[上轮生命周期记录](2026-11-14-qq-key-source-lifecycle.md)及[runtime pins](../../scripts/qq_napcat_runtime_pins.json)。
`dL` 注册目标命令的接收监听，按以下字段解码，将非空字符串交给 core 的 dbPassphrase；
后续数据库文件消费者再做 KDF。这是字段语义和消费者源码证据，不是 54395 的真实事件记录。

```text
QScope 已描述的接收回调：命令名 + 响应 payload + error
  → 命令恰为 OidbSvcTrpcTcp.0xcde_2，接收方向且完整
  → OIDB envelope：1=0xcde，2=2，3=返回码，4=body
  → body field 2 → inner field 1（UTF-8 passphrase）
  → 已有来源作用域及首页 MAC 认证
```

**尚待实证的交点**是 QScope 的这一个 MSF 回调是否在正常保护开启的 54395 中收到该命令，
其 payload 是否直接符合 NapCat 观察的 envelope，以及其中值能否认证同一会话的指定数据库。
不能根据“能收到其他 MSF 包”推定这三项成立。
原型不尝试解密未知内层、不猜前缀、不主动发送或重放协议请求。

QScope 根许可证是 [GPL-3.0](https://github.com/sj817/QScope/blob/0ee1533bb18c4ebdd918c355de27c204209acb3e/LICENSE)，
NapCat 是其有限再分发许可。未做将这些代码并入 Echo 的许可决定；本轮没有复制其 Hook、定位器、
布局读取、启动器或原生组件。只使用已公开的协议字段事实，独立写有界 wire 解析。
没有引入完整框架 API 或新密钥来源抽象。

## 原型实际做了什么

`observeCdeResponse` 只处理已经送达的事件，不提供 QQ 传输。
对非目标命令／发送方向，在访问 payload 前直接忽略。目标载荷最多 8192 字节，
拒绝截断、接收错误、错误返回码、畸形 wire、关键字段重复、缺失值或不合法 UTF-8。
仅解析三层必需字段，每层最多 64 项；不分析聊天消息，不缓存其他通信。

目标值只在内存中交给已有 `withAuthenticatedKey`，单次 MAC 成功返回固定状态；
错误即停，没有候选枚举。目标 payload 与口令 Buffer 在成功／拒绝路径尽力清零。
认证范围只有指定的加密 main 首页，不运行解密、SQLite 查询或报告；不证明全库完整或账号身份。

自建子进程在内存生成随机虚构口令、一页密文和目标响应，经启动时专有的 IPC 交给父进程。
父进程核对其直接创建的 child PID、单次随机会话标记、消息顺序及事件上限。
此处来源可信性来自自己创建并审阅的进程与私有 IPC 所有权，不来自消息自报的 QQ 版本。
同样的会话标记设计不能直接证明未来真实 QQ 的账号或密钥代际。

每例只建一个事件子进程，整个 Node 工作树在已有 Windows Job 内；
最多 8 条 IPC 消息、1 条目标接收事件，正常事件等待 3 秒；Python 外层上限 8 秒，释放预算另计 3 秒。
Node 父／子 V8 heap 分别设为 96／64 MiB，非整个进程 RSS 的硬上限。
父端 Ctrl+C、截止、拒绝时停止自己拥有的子进程；外层核验 Job 全树退出。
子进程也在 IPC 断开后退出，不留下等待中的虚构来源。

没有开放监听端口，没有 PID／QQ 路径／真实数据库入口。自建进程的 IPC 可以包含虚构载荷；
输出和文件只含固定状态及释放结果，不落盘口令、密文页或原始事件。
V8／IPC 的临时副本不能保证逐一清零，进程退出和 Job 回收是补充边界，不宣称防止系统分页或外部转储。

## 最小实机实验的准备条件与审批范围

已获得具体兼容依据，可以围绕同摘要模块的接收边界准备实验；当前还缺 Echo 自有、许可可用的
**仅接收／仅目标命令的原生适配器**，及其在自建原生进程中的 ABI、Hook 失败和卸载验证。
现有 Node 事件原型只解决适配器之后的处理，不能把“批准”当作缺失适配器已经实现。
不通过运行 QScope 完整宿主来填补这个缺口，也不把备用机／虚拟机或用户预先提供 key 作为前提。

原生适配器可审阅并通过自测后，才提交真实执行申请。申请必须逐项覆盖：

| 操作 | 最小范围与目的 | 风险及退出方式 |
| --- | --- | --- |
| 由用户选择一次退出并重新登录本机 QQ | 登录期事件不能假定登录后重现；仅一次，不主动重放请求 | 日常 QQ 会话暂时中断；由用户正常重开／登录，不自动结束现有 QQ |
| 指定主进程的启动期接收观测 | 核对路径、创建代际及已加载模块身份；仅一个接收边界，先读有界命令元数据，非目标不复制 payload | Hook 会修改进程内函数入口，存在崩溃／账号风控风险；安装失败不重试，不更改完整性保护 |
| 单个 `0xcde_2` 响应与单库认证 | 接收目标最多 8192 字节、单次、最长 120 秒；明确同意所选库前 5120 字节认证及必要的稳定性复核；不解密正文 | 响应本身可能含凭据，只有本机临时处理；输出事件发生／字段可解析／MAC 匹配布尔值 |
| 停止与清理 | 成功、失败、取消或超时均停止采集；等回调退出后恢复原函数；认证工作进程退出 | Hook 撤销及卸载必须有证据；若不能确认卸载，不热卸载 DLL，告知用户正常退出 QQ 后由地址空间回收 |

如果只能在关闭保护后安装，立即判定当前方案不满足边界。

以及观测停止／资源释放证据。只报告命令出现或其他协议流量不算完成。
