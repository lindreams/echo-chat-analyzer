# QQ 54395 登录观察点：离线根因与下一次验证边界

基线 `82e3bb2`。接续[两次真实观察及释放记录](2026-11-17-qq-login-lifecycle-preparation.md)。
本轮只检查源码和固定摘要的公开 QQ 模块磁盘文件，没有查询 QQ 进程、安装 Hook、取钥、
读取账号配置／数据库／聊天。没有重复原有测试、修改 GUI 或构建安装包。

## 结论：旧方案的成功事件选错，不是已经证明账号字段不存在

旧配置的五个原生地址均对应其标记的 JS 回调，已补查 native → deferred factory → 两种
invoke（inline／heap）→ JS proxy → named property 的完整链，不存在把成功地址误标为登出的证据。
但是它把 `onUserLoggedIn` 当作正常登录成功的首要候选，遗漏了 `onQRCodeLoginSucceed`。

固定版参考实现 `runtime/qq-napcat-candidate/napcat.mjs` 中：

- `xAe()` 的 `onUserLoggedIn` 设置“当前账号已登录，无法重复登录”的错误，不完成登录 Promise。
- 同一函数的 `onQRCodeLoginSucceed` 才设置登录成功、从对象取 `uin/uid` 并完成该 Promise。
- Shell 启动随后消费此身份来初始化自己的 session；它不是独立于成功回调的第二份身份事实。
- `onLoginConnected` 驱动登录服务准备；`getMsfStatus()` 也用于等待网络连接，不是本人在线证明。
- `getLoginList()` 返回历史候选，不能升级为当前本人。旧任务的原始账号类型 0 仍不是全局枚举定义。

本地参考文件 SHA256 与仓库 pinned patched 摘要完全一致；将所有 Echo patch 反向还原后，
SHA256 严格等于 pinned upstream：
`6a22c93373c8f73462658d57b00bc88164d7e5858c0fe2f178eb97d66d7cb3ba`。
因此这里审阅的是可验证的 4.18.34 上游登录实现，不依靠当前搜索摘要或字段名称猜测。
在线上游当前已无法取得先前源码路径，本地固定摘要参考是本次语义证据；没有执行该 bundle。
参考源码不进入产品运行依赖，也不恢复其二维码、登录操作或 NapCat runtime。

**这证明旧候选语义不足，以及有依据的新成功观察点；尚不证明普通 QQ 的登录按钮一定经过
新回调，更不证明一次成功通知足以持续证明当前在线。**

## 注册、保存与派发证据

所有地址均为同一固定 wrapper SHA256 下的 RVA，不是进程地址或账号信息。

| 路径 | 静态证据 |
| --- | --- |
| JS 注册入口 | `0xdb6f3a` 的 `addKernelLoginListener` shim，取得一个 JS 实参，创建共享 listener，unwrap 服务，再调用服务虚表 `+8` |
| listener 构造链 | `0xdb7123 → 0xdc1e3f → 0xdc1ed6 → 0xdc1f5c → 0x22a9644`，最后经 tail-jump 到实际构造器 |
| JS 对象保存 | 构造器保存 NAPI env，调用 `napi_create_reference`，refcount 为 1，将引用保存到对象 `+0x20`，vtable 为 `0x4436218` |
| 移除接口 | `0xdb7160` 的 `removeKernelLoginListener` shim，委托服务虚表 `+0x10`；原生服务内部容器与所有移除触发条件尚未证明 |
| 回调触发后的保存 | 原生虚方法取得自己的共享生命周期上下文、保存 this／实参到 closure，deferred factory 提供 inline／heap 两种 invoke，再进入命名 JS proxy |

旧实验只是 Hook 已有原生函数入口，没有调用注册接口添加自己的 JS 监听器。两次至少有一个
既有 listener 真实调用进入；这排除了“完全没有任何监听回调”的解释，但不能证明所有账号 session
共用同一监听实例。没有当次注册／移除时序回执，不能声称已证明注册早晚就是根因。
初始连接事件可能在 armed 前已发生；缺少它也不能反证登录没有发生。

| 回调 | 槽／原生入口 | deferred factory → inline invoke → JS proxy |
| --- | --- | --- |
| `onUserLoggedIn` | 13／`0x22aa276` | `0x22ae262 → 0x22ae384 → 0x22ae399` |
| `onLoginState` | 7／`0x22a9bfa` | `0x22ac730 → 0x22ac858 → 0x22ac86d` |
| `onLogoutSucceed` | 11／`0x22aa106` | `0x22adbe2 → 0x22add04 → 0x22add19` |
| `onQRCodeLoginSucceed` | 8／`0x22a9cc8` | `0x22acb0c → 0x22acc1c → 0x22acc31` |
| `onLoginConnected` | 1／`0x22a9706` | `0x22ab102 → 0x22ab224 → 0x22ab239` |

断连与 connecting 的旧地址也逐条验证，两种 invoke 都落到各自正确 proxy。
核验脚本为 `scripts/spikes/qq_native_event/login_lifecycle_source_check.py`，只读磁盘，不产生 armed。
它补上了旧 layout check 没有校验的 factory／invoke 连接，未把互相独立的名称引用当作调用链。

## 为什么两次只看到登出

可以确认：两次回执里的 `onLogoutSucceed` 标签与实际入口相符；旧集合没有监听正常成功候选。
第二次仅过 8641 毫秒就收到该事件，随后人工在线确认因缺少原生身份被拒绝，不能把全部失败
归因于首次接近超时。正常成功走另一条回调时，旧集合自然不能记录它；但当次是否真的走了它，
没有采样证据，仍待下一次最小验证。

不能确认：QQ 为什么在登录操作期间触发 logout，是内部旧 session 清理、其他监听上下文还是
其他流程。没有调用者／服务所属上下文的运行证据，**不把其中任何一种写作真实原因**。
同样没有证据把原生状态枚举或现有监听注册时机定为唯一原因。

| 假设 | 本轮结论 |
| --- | --- |
| 地址或事件标签错位 | 已检查完整派发链，旧五个点未发现错位 |
| 正常成功通知选择错误 | 有固定上游源码证据，旧 User 通知不能承担该角色；遗漏 Success 点 |
| 账号值根本不存在 | 不成立为普遍结论，新 Success 对象有明确 uint64 `uin` 字段 |
| 注册时机错误／QQ 实际流程不经过这些类 | 尚无当次注册与正常登录完整调用证据，不能凭缺失事件定因 |

## 新候选的最小字段及仍缺的生命周期证据

新入口 `0x22a9cc8..0x22a9d5c` 的 ABI 是 `this`（RCX）与对象指针（RDX），**不是**旧 User
入口的 uint64 标量。它调用 `0x22a9dc2` 复制该对象，其中原对象 `+0x30` 的 8 字节被原样复制。
proxy `0x22acc31` 跳过 closure 头，再调用对象转换器 `0x22acdaa`：转换器读取对象 `+0x30`，
按 uint64 转十进制字符串，经 `napi_set_named_property` 写入确切属性 `uin`。
同一对象还含 account、mainAccount、uid、nickName 等字段；下一次不读取这些字段。
因此最小新增数据只是该回调对象的 **8 字节 UIN**，加既有角色 vptr、来源一致性和进程代际。

从固定参考还可知，离线失效并不只来自 LoginListener：`initNapCatCoreListeners()` 还处理
MsgListener 的 `onKickedOffLine` 和 ProfileListener 的 `onSelfStatusChanged`。前者可能携带
私人提示，后者有 status；本轮不读取这些运行时对象、不扩大 Hook。参考中“非 20 一律在线”
不能直接搬为 Echo 的可信规则。这些证据只说明**原五回调不足以被宣称覆盖全部离线状态**。

后续生产绑定应由真实成功声明建立单调登录代际（进程代际＋可信来源实例＋成功事件序号）。
登出、连接转换、失败、来源移除／替换、失联、进程退出或身份冲突立即作废旧代际并取消获取；
同 UIN 重登也必须新建代际，不能靠目录、旧账号、随机传输标签或人工确认恢复。离线／踢下线
等路径若未证明有可靠失效来源，就不能给出可持续复用的当前在线绑定。短 TTL／周期重复采样
不替代完整失效来源。

## 下一次应验证什么（本轮不执行、不要求登录）

最小准备已明确入口、ABI、字段来源、版本摘要和验收边界；旧 `--approved-single-run` 入口
已在任何进程访问前拒绝为 `login_success_observer_required`，防止重用错误观察方案。
没有将 Success 对象按旧标量 ABI 强行接入，也没有启用新的真实 Hook；新原生 reader 尚需按
这里的对象 ABI 做最小接线与虚构对象边界验证，不能把静态检查通过称作新 Hook 已可 armed。

若继续此候选，单次受限验证只应回答：

1. 通过固定摘要、入口边界／完整函数摘要及角色校验后 armed。用户用 QQ 客户端原有正常方式
   登录；不要求切换成 Echo／NapCat 二维码。不尝试密码、验证码或登录请求 Hook。
2. 新 Success 原生回调是否确实在这次普通登录后发生，8 字节 UIN 是否等于私有独立本人参考；
   同一 QQ 进程代际及监听来源是否成立。只输出匹配布尔值、回调计数和顺序，不打印身份或对象。
   回调没来、字段不符、来源不唯一或未知时停止，不换登录方式再试，也不以旧 User 通知通过。
3. 成功候选成立后，用户按提示正常退出登录。必须先见原生失效，再允许同进程同账号重登；
   新成功必须得到新代际，旧代际保持无效。进程退出／重启就停止，不二次注入或沿用旧绑定。
4. 保留原总观察期限与记录上限；未知状态、争用、序号缺失和超时拒绝。停止回执、自有资源释放
   与用户最后正常退出后的组件卸载分别核验。不取钥、不解密、不查聊天、不重复路径／锁实验。

这次实验首先证实普通登录能否经过候选，再验证该受控登出路径；不能一次外推为所有踢下线、
换号或对象销毁路径已安全。若只能证明单次身份，仍不得启用运行中连续自动绑定或宣称 GUI 完成。

## 产品级替代与本轮停止位置

若普通 QQ 不经过此成功通知，或失效来源始终不能证明，停止这条持续在线绑定路线，不再堆新回调。
更简单的候选是明确的“离线账号资料分析”：由用户在账号数据源列表中明确选择并授权，正常退出
QQ 后冻结输入；本人是所选且验证通过的快照账号，界面不宣称自动识别当前在线账号。这仍须保持
目录／加密认证／逐会话校验，密钥获取另按已验证范围授权；不是要求手填账号或群号的旧入口。
它需要负责人认可产品流程变化，本轮不实施。仅要求 QQ 退出可以简化一致性和生命周期，却**不能
独自补出可信在线本人**，不能把退出步骤包装为原目标已经成立。

本轮在“已找到有静态调用链及固定上游支持的成功候选，但没有新的运行证据”处停止。
只完成新增静态证据检查和旧入口的提前拒绝核验，不重复已有测试。差异格式检查通过。
未取钥、未读取真实聊天、未改 GUI／main，未合并、推送或打包。历史受保护资产原位保留；
本轮无私人数据的静态反汇编及隔离环境留在忽略的 build 范围，研究审核收尾时再处置。
