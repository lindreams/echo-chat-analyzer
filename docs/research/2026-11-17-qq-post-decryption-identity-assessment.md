# QQ 离线导入：解密后本人身份校验评估

接续[离线时序验证](2026-11-17-qq-offline-import-feasibility.md)。本次只检查仓库源码，
并运行隔离的虚构样本；没有访问真实 QQ、真实账号资料、安装模块或新的实验数据，
没有新增 Hook，也没有继续登录实验。

## 结论与停止边界

**最终账号匹配可以放在认证解密之后；取钥之前并非必须已经获得本人身份。
但当前已验证的数据模型没有提供独立的数据库本人身份来源，因而此方案尚不能准入。**

如果存在经过可靠验证的库内本人角色字段，可以按以下顺序实现：明确授权账号 →
本次有界凭据 → 完全退出 QQ → 固定一致快照 → 逐页认证解密 → 读取内部本人身份 →
严格匹配授权账号 → 发布会话列表和允许分析。匹配前，明文只能处于受保护的任务临时空间；
取消、缺失、冲突或失败须关闭任务并清理，不能先把会话交给 GUI。
这种结构不要求持续在线登录回调，也不要求凭据响应本身一定携带 UIN。

当前缺的仍然只有一项前置证据：**本次凭据与所授权账号的独立、可核验关系。**
解密后可信本人字段和同次取钥请求／响应的可信账号关联，是解决同一缺口的两条候选路径。
不能通过移动校验顺序，把原本不存在的独立证据补出来。

本结论限定于现有源码与此前可靠验证的字段；没有断言所有 QQ 数据库都不存在本人字段。
按本轮停止条件，不编造字段、不新增逆向或真实采集、不以传入账号代替认证，暂不接正式 GUI。

## 已核对的来源与语义

| 来源 | 实际含义与数据流 | 能否独立确认数据库本人 |
| --- | --- | --- |
| `group_msg_table`／`c2c_msg_table` 的 `40033` | 每条消息作者；同库包含本人和其他人 | 不能；出现次数、共有发送者或发送时间都没有本人角色保证 |
| `40027`、`40030` | 会话分区与会话对象；私聊对端推导还使用外部 `self_uin` 排除本人 | 不能；会话对端不等于数据库所有者 |
| `profile_info_v2`／`profile_info_v6` 的 `1002`、`1000`、`20002` | UIN、UID、昵称；按显式成员集合查名称 | 不能；已验证的是成员身份映射，没有本机本人角色字段 |
| `group_member3` 的 `60001`、`1002`、`1000`、`64003`、`20002` | 群、成员 UIN／UID、群名片、昵称 | 不能；群成员关系和名称不声明数据库本人 |
| `group_list`／`group_detail_info_ver1` | 群号和群名称 | 不能 |
| Provider 输出的 `payload.self` | `_self_context(self_uin)` 规范化调用方参数 | 不能；用它匹配同一调用参数构成循环验证 |
| Adapter 的 `is_self` | 将消息作者与 `payload.self.value` 比较 | 不能；它消费本人上下文，不发现本人 |
| 独立通路 `_materialize` | 将 `selection.account` 传给 Provider 和名称附加器 | 不能；所选账号及“我”的展示不是独立身份证据 |
| 旧 Direct DB `manifest.identity` | `snapshot.mjs` 从运行时 `core.selfInfo.uin` 前后读取并写入 manifest | 不是库内字段；离线读取 manifest 不能继承旧运行时的证明 |
| 旧私聊 nudge 的 `owner_uin` | 来自运行时 `self_info`，并与外部本人上下文比较 | 不是库内本人来源 |
| 真实报告核验中的 own／other 计数 | `finish_report`、`audit_adapter` 使用传入的 `self_uin` 分类并相互核对 | 证明解析一致性，没有独立发现数据库本人 |

因此，账号在联系人或消息作者中出现、UID／UIN 关联正确、名称齐全，以及 SQLite 完整性或
页面 MAC 成功，都不能单独证明该账号是这份数据库的本人。目录名称、旧实验参考和历史候选
同样不能补足该角色证据。现有 self identity 测试也明确用运行时 manifest 或 payload 注入身份，
没有覆盖从库内发现本人的实现。

## 新增的虚构反例验证

扩展既有 [最小时序诊断](../../scripts/spikes/qq_offline_import_check.py)，不另建生产身份抽象。
在原有加密 SQLite 样本中加入两位虚构作者的群聊、私聊记录；沿用生产快照、认证解密、
Provider 和 Adapter。先完成认证解密和完整性检查，再对每份相同数据库执行：

| 传入本人上下文 | 两条消息的 `is_self` | 说明 |
| --- | --- | --- |
| 虚构 A | `true, false` | 输出依赖 A |
| 虚构 B | `false, true` | 输出随输入对调 |
| 未出现在消息中的虚构 C | `false, false` | 此层不是账号准入器，不会因账号未出现而拒绝 |
| 缺失 | `null, null` | 保持未知，不从发送者猜测本人 |

两份已认证数据库、群聊和私聊均得到上述结果；各组读取前后数据库 SHA256 不变。
原有不同目录标签下均能认证的反例仍通过。这不声称真实 QQ 会跨账号复用凭据，
而是证明现有 API 的密码认证和本人分类没有独立的账号准入语义。
它也不是拟议最终身份闸门的验收；该闸门因缺少真实身份来源尚未实现，不能用虚构 owner 表
通过测试后宣称真实产品成立。

本次验证同时通过原有取消、超时、认证页损坏、消费异常、异步消费拒绝、可观察凭据缓冲区
清零和 owned Job 释放检查。未增加用户数据访问或放宽快照条件。
使用当前工作区显式虚拟环境，确认 Python 版本、实际导入位置、目标 runtime／dev 依赖范围、
pip 一致性和 pytest 可用；未安装依赖。脚本隔离用户目录及环境，只启动自有虚构写入者和
Node worker，唯一替代的系统观察仍是虚构写入者退出状态。脚本退出为 0，自有 helper 释放。

## 最小凭据／账号元数据关联评估

现有 `identity_metadata.inc` 在发送任务上读取账号字符串候选和原始类型，
而 `adapter.cpp::inspect_response` 只复制目标命令的响应凭据 payload。
它们是不同观察配置；当前导出的固定记录没有共同的请求序号或等价关联标识。
命令一致、同一进程、时间接近、原始类型曾为 0、历史候选曾匹配本人，都不足以排除多账号误配。
日志锚点包含 `seq` 只证明存在日志格式，不能当作已经导出和核验了关联字段。

最小候选是：在同一受准入进程代际内，明确发送任务账号字段的 UIN 语义，
并将这一个取钥请求与这一个成功响应按可信、唯一的请求标识配对；身份冲突、歧义、
重放或代际改变均拒绝。再让该响应凭据认证固定数据库，才有独立于目录和授权输入的关联。
现有实现尚未提供上述证据，本轮不假设字段偏移、不安装新 Hook，也不新增登录观察。
单次登录成功曾匹配 UIN 的历史结果与本次凭据不属于同一条已证明关联链，不能拼接使用。
