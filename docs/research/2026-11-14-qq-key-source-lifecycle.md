# QQ 54395 密钥来源与生命周期：本轮证据及接口

结论：有新的来源线索，但**还没有能在当前边界下实际接入的可信 Windows 54395 密钥来源**。
本轮补上独立的来源合同及虚构生命周期验证，没有实现真实 provider，也没有申请或执行业务内存读取。
不继续增加候选或扩展扫描范围。

## 证据锚点与本机静态结果

本轮只核对已锁定社区实现，不重新调查生态。Echo 的
[runtime pins](../../scripts/qq_napcat_runtime_pins.json) 固定 NapCat 4.18.34。
本地 bundle SHA256 实测与 pins 中补丁后摘要一致：
`e362b232cf225e92253086e14a24c055adfbb09da4e9b0f8988c75e5ea49137e`。
这绑定的是可审阅的框架源码，**不代表该框架在 54395 实机运行成功**。
下文行号为该 bundle 的源码位置，不是 QQ 内存地址。
该框架采用有限再分发许可，本轮仅分析生命周期，没有复制其监听器、原生组件或解密实现；新增接口为自有研究代码。

沿用已完成的授权模块探测事实：当前活动资源为 9.9.37-54395，只有主进程加载了与该资源路径匹配的
`wrapper.node`。该探测没有证明库与账号／进程绑定，也没有校验已加载映像的字节摘要。
本轮只读安装元数据及磁盘上的该模块，没有重新探测进程或打开聊天库。

磁盘模块 SHA256：`fed532ad58d2404dcedf2858554e8fa52a5f4e65b271c008d2faca4011d7d4a2`。
模块内存在 `nt_sqlite3_key_v2: db=%p zDb=%s` 诊断字面量。
自写一次性检查只返回存在与否和公开模块摘要，不输出偏移，不定位内存，不加载或执行模块。
文件身份、大小和修改状态前后校验；复用现有读取器的 Windows stat/fstat 时间口径处理。
检查脚本和脱敏回执留在本次忽略的实验目录，未提交安装文件或本机路径。

这个字面量与 [QQBackup 固定源码的静态定位线索](https://github.com/QQBackup/qq-win-db-key/blob/5c643c39bdc65a7ce3ecc414052fdfd93d5f9107/scripts/windows/ntqq/windows_ntqq_get_key.ps1)
一致。它只证明磁盘模块含有该字面量；不能证明对应函数执行、ABI、参数来源、上下文寿命或可外部读取的指针。
上游默认通过调试启动及断点读取参数，包含写目标进程的操作；本轮未运行其脚本或移植机制。

## 组件关系：源码事实和推断分开

| 阶段 | 已核对的源码事实 | 对 54395 仍不能推出的结论 |
| --- | --- | --- |
| 客户端／框架初始化 | bundle `dL`（82857 起）选择活动 wrapper，并在核心对象创建前注册 `OidbSvcTrpcTcp.0xcde_2` 监听 | 正常 QQ 是否公开同等监听接口；54395 是否仍发相同事件、何时发送 |
| 会话响应供钥 | 82874 起仅处理接收类型，解码外层 body、内层 field 2 → field 1；21576 起将 value 定义为 STRING，非空值暂存为 `a` | 该值在本机 54395 的真实性、账号／数据库绑定、是否每次登录或打开库都能取得 |
| 核心对象持有 | 82950 在 core 创建后转交早到值；Echo 既有补丁使后到响应也更新 `core.dbPassphrase`，以值变化递增观察代际 | 观察代际不是腾讯 key epoch，不证明退出登录清零、轮换频率或驻留位置 |
| 数据库消费者 | `TY.getPassphraseBuffer`（33713）复制 core 中的值；`openDatabase`、`decryptDatabase`（33733、33814）把它交给独立文件解密函数 | 这是框架自己的离线消费者，不是 QQ 原生打开数据库的完整调用栈 |
| 密钥形态 | `bY`（33380 起）将传入 passphrase 与库盐做 PBKDF2，得到 raw key；再建立页认证密钥 | passphrase 不是 32 字节 raw key；不能把之前 raw literal 窗口形态当成唯一来源 |
| 后续读库 | 框架先解密再用 SQLite 打开缓存；原生 QQ 磁盘模块另含 key_v2 诊断字面量 | 两条证据之间尚无 54395 的调用关系、实例绑定和上下文生命周期证明 |

最重要的约束是监听器本身的来源。`uAe`（82157 起）加载 `native/packet/MoeHoo.*.node`；
其 `init`（82283 起）以版本和架构索引 send/recv 数据，调用原生 `initHook` 后分派事件。
当前固定 bundle 的表内没有 `9.9.37-54395-x64` 项，也没有 54395 实测回执。
因此 `onCmd` 不是现成官方进程外数据接口，移走框架 API 并不会自动消除其原生介入依赖。
没有运行这些原生组件、注册回调、发送协议请求、捕获网络流量或启用 bypass。

**合理推断**：登录会话向数据库初始化层提供 passphrase，原生数据库层再持有派生后的加密上下文，
并可用于后续页读取。前半段有框架源码线索，后半段符合
[SQLCipher 的 key 设置和按需派生合同](https://www.zetetic.net/sqlcipher/sqlcipher-api/#sqlite3_key)。
但 QQ 私有实现的完整调用链并未公开，不能把这一推断写成 54395 已验证生命周期。
`sqlite3_key_v2` 是给自己持有的数据库连接设置 key，不能从另一个进程查询 key。

[qq-local-interface 固定 README](https://github.com/Ethan-Wang-dev/qq-local-interface/blob/587b63e880070849240dde3f2bc447d7a7e8b35a/README.md)
仍只提供 macOS 6.9.85／36362 的验收和 LLDB 入口；它支持来源与认证分离的设计，
没有补齐 Windows 54395 的可用入口。本轮没有重新审计或移植其取钥器。

## 来源接口与生命周期

参考 [WeChatKeyService](../../src/qq_chat_analyzer/application/wechat/wechat_key_service.py)：
复用“来源负责 acquire，单一 owner 负责释放，cancel 只发信号，失败不复用陈旧凭据”的职责边界。
不迁移其 Hook／注入实现，也不沿用将密钥暴露到环境变量的行为。
候选验证器只负责认证已给定窗口的内容，不能充当可信来源。

```text
已审阅 provider（目前缺失）
  acquire(binding, control) → 一份临时 lease
  lease = kind + material Buffer + binding + isCurrent()
    → 检查来源代际与声明绑定
    → 复用候选 codec 首页 MAC 认证
    → 再检查 isCurrent / cancel / deadline
    → 同步 consume(raw32)，只在此作用域借用
    → 清零 material / raw 副本并调用 provider.close()
```

binding 明确版本、会话代际、加密 profile、待认证 5120 字节的摘要。
provider 必须独立证明这些字段；照抄请求不构成来源证据。MAC 命中证明当前页与 key 匹配，
不证明授权、完整库、账号身份或来源可信。摘要只绑定冻结的单页观察，不代替后续安全快照。

kind 区分 `raw`（32 字节）与 `passphrase`（1–4096 字节）；后者只调用现有已验证 profile 的 KDF。
源码显示的口令字符串由未来 provider 在私有作用域编码为字节，不以 raw 形式误用。
调用方不能取得返回 key，结果只有固定认证状态；密钥只可在同步 consumer 作用域使用。
目前没有默认真实来源、文件密钥缓存、自动地址发现或轮询；缺来源直接 `trusted_source_unavailable`。

每个来源实例仅使用一次，重入不会抢走当前 owner。来源过期、代际／页绑定不符、认证失败、
取消、截止或异常均退出；部分 acquisition 失败也要求 `close()` 清理已拥有资源。
close 未明确确认释放则拒绝返回成功。Buffer 尽力清零，不声称 JS 运行时、系统分页或外部转储绝对清零。

这个小接口只支持可信、同步、有界的来源，使用阶段边界检查取消和截止，**没有硬抢占保证**。
不能直接接入可能阻塞的原生调用或异步 provider。将来若有可信真实来源，需要放进已有 owned Job
工作进程，另验证超时及全树退出；当前没有为不存在的来源新建工作进程或并行状态框架。
consumer 也须同步有界；代际检查不具备跨进程原子性，回调中的副作用无法自动回滚。

本轮验收仅使用随机虚构 key／口令、已有 encoder 的一页密文和自有内存来源，没有新增解密测试。
覆盖来源缺失、两种形态、未认证不得交给 consumer、四项绑定错配、来源失效／轮换、取消与截止、
部分取值失败、consumer 异常、清理失败和重入。脱敏结果为通过，不代表真实 54395 取钥通过。

运行研究验收前隔离 HOME、USERPROFILE、APPDATA、LOCALAPPDATA、TEMP/TMP 等到本次实验目录，
清除 NODE_OPTIONS/NODE_PATH；执行 `node scripts/spikes/qq_key_source_check.mjs`。
Python 只用于一次磁盘模块检查，显式使用已核验项目 venv，核对当前 src 导入及依赖，无安装升级。

## 下一步缺少的关键证据

本轮新增了“会话响应供给 passphrase”和“54395 磁盘模块保留 key_v2 标记”两项具体依据，
但尚不能把二者连接成符合当前边界的真实来源。具体缺少：

1. **可访问入口**：54395 可由进程外调用的受支持本地 API／IPC／用户主动导出机制，
   或有源码及该版本证据、无需 Hook／注入／保护绕过的密钥提供组件。
   现有 packet listener 依赖原生 Hook；macOS LLDB 不适用；旧版堆扫描不补足这一条件。
2. **对象与寿命证据**：该入口的签名、返回表示、进程／会话代际、账号／库绑定，
   以及初始化后能否重新取得、登录退出／轮换时怎样失效和释放。
   静态诊断字符串没有给出这些内容，也不能据此指定读取窗口。
3. **版本对应实证**：同一磁盘模块对应的 54395 受控取值结果，可在明确授权下只以目标库认证结果判断；
   不需公开密钥或聊天正文。现有路径匹配和其他版本的运行结果均不能替代。

因此本轮不提出真实进程内存读取方案，也不要求用户重复批准一个仍未定位的窗口。
后续可先补该版本的公开接口／静态调用关系证据；只有能确定可访问对象及有效寿命后，
才有条件提出读取对象、最大范围、影响及清理方法明确的单次实机实验。
这与现有解密器是否能处理已知密钥无关，继续增加虚构候选不能解除此阻塞。

本轮源码与记录待人工审核；忽略实验目录保留一次性脚本及脱敏回执用于复核，审核后决定处置。
不保留任何真实 key／内存样本／聊天内容。
