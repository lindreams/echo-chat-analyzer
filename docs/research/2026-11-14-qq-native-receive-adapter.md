## 接收位置：本机磁盘模块的新证据

目标限定 Windows x64 QQ 9.9.37-54395，`wrapper.node` 文件 SHA256：
`fed532ad58d2404dcedf2858554e8fa52a5f4e65b271c008d2faca4011d7d4a2`。
该摘要与上轮本机静态检查及
[QScope 固定 profile](https://github.com/sj817/QScope/blob/0ee1533bb18c4ebdd918c355de27c204209acb3e/collectors/qqnt-windows/profile.json)
一致。没有以客户端显示版本替代模块身份。

本轮自写一次性只读 PE 检查，在该磁盘文件上取得以下结果：

- 已公开的 32 字节接收前缀有 **396** 个候选，因此放弃“前缀唯一”定位假设。
- `DidRecvResponseData` 与接收日志字面量的 RIP-relative LEA 引用，各自落在一个 PE 异常表函数中；
  两个语义锚点与前缀候选的交集只有一个。
- 函数 RVA 为 `0x1c39de8`，异常表结束 RVA 为 `0x1c3a274`，共 1164 字节。
  这些是固定版本**函数偏移**，不是密钥地址或待扫内存窗口。
- 对该范围使用已有 MSVC dumpbin 只读反汇编，无模块加载／执行、无进程访问。

自有代码根据固定摘要使用上述 RVA，并复核执行节、前缀、异常表边界及两个语义引用；
任一不符拒绝，绝不搜索其他版本、其他函数或扩大范围。
初版前缀准入假设是在静态检查发现多匹配后收紧的，没有在 QQ 中试错。

反汇编中的直接事实：

| 位置／用途 | 已观察的机器码行为 | 可得结论 |
| --- | --- | --- |
| 函数入口 | 保存 RCX，解引用 RDX 中的 owner；保留 R8D | 与 `self, response-owner, error` 的 x64 调用约定相符 |
| RVA `0x1c39e3f` 起 | 取响应 `+0x20` 作为字符串对象；取 `+0x38` 指向容器并读 begin/end；后面以差值记录 data_size | 命令和载荷已经是独立对象，不是只给一个未经分包的 socket 缓冲 |
| 原生分派前 | 将这些字段用于命令／长度日志，并将同一响应交给注册消费者 | 入口就具备筛选目标命令及复制有界响应的条件；不需另 Hook 发送端 |

“+0x20 为 24 字节字符串、+0x38 指向 byte vector”的布局与社区事实一致；
本轮用原生宿主的短字符串和保留堆分配的字符串两种布局实际验证自己的读取代码。
这里只读明确回调对象，不枚举或搜索进程堆。

**语义判断的限度**：这里已处在 QQ 的协议响应分派层，具备明文命令元数据和独立载荷。
但机器码日志和通用流量验收不能证明目标载荷没有内层加密／封装。
NapCat 已有源码支持在同名接收事件上直接解析 OIDB 字段；QScope 的 profile 也明确保留内层可能加密的限制。
本轮没有真实目标事件，因此只能判断“有依据进行一次解析条件验证”，不能宣布真实 payload 已可解析，
也没有证据认定此位置只提供不可解析密文。
若真实目标事件不符合现有解析合同，返回失败并停止，不探测其他 Hook 点、不猜解密方式或前缀。

## 独立代码与依赖

QScope 和 NapCat 仅作为接收位置、布局与字段语义的参考；没有复制其 GPL／有限许可实现。
Native 不实现 Protobuf、KDF、MAC 或 Provider，读取出的单个目标响应只交给已有 JS 组件。

Hook 基元使用 [MinHook v1.3.4 固定 revision](https://github.com/TsudaKageyu/minhook/tree/c3fcafdc10146beb5919319d0683e44e3c30d537)，
属于 [BSD 两条款及附带 HDE 许可](https://github.com/TsudaKageyu/minhook/blob/c3fcafdc10146beb5919319d0683e44e3c30d537/LICENSE.txt)。
固定 11 个源码／许可文件的 SHA256，从源码本地编译，不下载运行第三方二进制。
完整许可随本机编译产物保留；没有将依赖安装到系统、Python 环境或正式发行配置。

MinHook 安装／撤销会短暂枚举和暂停当前进程线程，并改写函数入口。
上游会跳过无法暂停的线程，不能把本轮自建进程成功外推为 QQ 所有线程可控或任意并发下安全。
不修改该库来规避权限失败，不关闭客户端保护；真实安装仍需单独评估并批准。

## 原生边界和生命周期

组件只导出进程内 `EchoInstall`、`EchoRead`、`EchoStop` 和固定状态查询，不包含远程注入、调试启动、
QQ 启停、目录修改、注册表映射或安全开关。

正式目标变体 `echo_event_54395.dll`：

- 只查已加载的 `wrapper.node`，不主动加载 QQ 模块；固定版本与文件 SHA256 准入，验证上述函数条件。
- 固定一次安装尝试，只有安装 owner 线程能读／停；失败不自动换目标或重试。
- 在一次接收回调内，仅沿 owner → response 读取有界命令；命令不符不读 payload 指针或内容。
- 只对匹配目标、无接收错误的响应复制一份完整载荷，最多 8192 字节；超限或非法指针拒绝。
  返回原函数的结果，传回相同参数，恢复调用原函数前的 LastError；原函数异常继续传播并清掉 in-flight 计数。
- 单次采集最长 120 秒。读取等待单次最多 2 秒，owner 应循环响应取消；停止先关闭采集并清零，
  再撤销本组件的 Hook，最多等待 100ms 回调退出，未知时返回失败。

没有后台线程写文件或网络；接收路径没有 Protobuf 解码或 KDF。原生只持有一个 8 KiB 槽。
公开 API 返回载荷意味着 bootstrap/消费者必须拥有可信私有传输；本轮只实现了自建宿主的匿名管道，
尚未实现 QQ 中的载入／传输 bootstrap。

**停止与卸载不是同一件事**。QQ 变体不导出释放 trampoline／热卸载的 API；
即使 in-flight 暂时为零，也不能证明没有线程已经跳入 detour 但尚未计数。
停止后保留 DLL、trampoline 及其事件句柄至 QQ 正常退出，状态如实报告资源仍驻留，不伪报完全释放。
这是一轮单次验证组件的保守策略，尚不构成正式产品的长期连接生命周期方案。

自建宿主变体 `echo_event_fixture.dll` 使用编译时独立开关：只接受本次宿主 EXE 的编译后 SHA256，
在自有导出函数上安装 Hook，额外导出 `EchoReleaseAfterHostJoined`。
宿主停止并 join 所有调用线程后，才移除 trampoline、释放句柄并 FreeLibrary；
随后检查入口原始字节和 DLL 不再加载，再次调用原函数，确认宿主可继续运行。
该释放入口不存在于 QQ 变体，不能用 fixture 选项放行未知 QQ。

## 实际编译与运行

使用本机已有 Visual Studio 2022 MSVC x64 14.43.34808，Windows SDK，Node 24.16.0 和项目 Python 3.13.9。
显式 venv、当前 src 导入和所需依赖一致性检查通过；未安装或升级环境。
构建／自测前隔离 HOME、USERPROFILE、APPDATA、LOCALAPPDATA、TEMP/TMP 等到任务自有目录，清除 Node 注入选项。

```powershell
# 使用当前仓库 build 下的自有输出目录；不指向安装目录。
& scripts/spikes/qq_native_event/build.ps1 -BuildRoot <owned-build-root>
.venv/Scripts/python.exe scripts/spikes/qq_native_event/check.py <owned-build-root> <new-owned-check-root>
```

三个二进制均实际编译完成，MSVC /W4 下无本轮代码警告；自测先核验构建摘要再运行。
已有 Windows Job 包含 Node 与其原生子进程，外层 10 秒截止，释放预算 3 秒；
Node 对单宿主另设 5 秒上限，匿名输出管道最多 8208 字节。
故障退出只输出固定代码，不输出原始 native 字节或错误文本。

通过的定向验收：

- 原生短／堆字符串布局的目标回调均实际抵达旧 JS 解析器，并对指定虚构首页 MAC 成功。
- 非目标命令的 vector 指向 PAGE_NOACCESS，未被读取；目标 vector 非法时 SEH 拒绝，宿主继续运行。
- 取消、截止、MH_CreateHook 后模拟失败回滚、错误版本拒绝、QQ 变体在无匹配模块宿主中拒绝。
- 回调仍阻塞在原函数时，停止报告未排空、释放拒绝；放行并 join 后才成功释放。
- 原函数异常向宿主传播，in-flight 清零；每例入口恢复、DLL 卸载、资源释放后原函数仍可调用。
- 每次工作 Job 全树退出并关闭；运行目录不产生原始数据文件，最终只写脱敏结果。

宿主只处理自生成的虚构载荷，事件和密文首页只经内存／匿名管道。
没有在 stdout 日志、文件、命令行或环境中持久化密钥或原始流量。
JS／CRT 临时副本和系统分页仍不能绝对清零，不能将进程退出等同于密码学擦除保证。

未覆盖：真实 QQ 安装 Hook、真实加载映像的准入正例、真实目标事件、真实库认证、客户端风控、
QQ 中停止后完整热卸载。没有运行正式应用／全量测试；修改全部隔离在研究目录，使用上述实际原生定向验收。

## 下一次本机真实验证：最小范围及恢复

本轮没有执行任何下列真实操作。组件已具备接收与停止能力，但真实 QQ 的启动期载入及受限 IPC 胶水尚未实现；
不能用本轮自建宿主命令直接接入 QQ，也不能承诺任意时刻附加都能看到登录事件。
bootstrap 必须在真实执行前独立审核、自建宿主验证，并确保不在 DllMain／loader lock 中安装 Hook。

拟申请的真实实验限定为：

1. 用户选择一次正常退出／启动本机 QQ、手动登录；不由工具杀现有 QQ，不要求备用机／虚拟机。
   在正常保护下装载本轮自有 DLL，若被拒绝即停，不加 `--no-sandbox`、补丁或绕过保护。
2. 只绑定一个主进程的路径、创建代际、54395 资源及匹配的模块文件；在数据库初始化前安装**一个接收 Hook**。
   Hook 安装涉及进程内代码改写及短暂线程暂停，有客户端崩溃、卡顿和账号风控风险；必须单独批准载入及安装方式。
3. 最多 120 秒、一个目标事件；只读命令元数据筛选，目标最多 8192 字节，不复制其他通信。
   另单独批准指定库的加密首页认证：前 5120 字节及必要的前后稳定性复核，不解密／读取聊天正文。
4. 只输出事件发生、字段解析成功、MAC 匹配及停止状态；成功或任何拒绝即关闭观测，不重放登录请求。
   若载荷仍加密／不符合字段合同，停止该接收点方案，不扩大 Hook 或内存范围。
5. 调用停止并保留 DLL／trampoline，告知资源仍驻留；由用户正常退出 QQ 后地址空间回收，再正常重开即恢复。
   未确认排空时禁止 FreeLibrary；安装失败检查资源是否驻留，未知时同样请求用户正常退出。
   不执行任何结束日常 QQ 的自动恢复动作。

这个计划还不是可直接执行的 QQ 命令。本轮结束于可审阅、已自测的原生接收组件，等待后续决策与逐项授权。
