# QQ 54395：受限载入与认证 IPC 的实机前验收

本记录包含实机前施工和随后逐次获批的真实实验。后续第二次实验已在本机 QQ 54395 上
捕获目标响应、成功解析并认证实际数据库首页，且用户正常退出后的资源释放已确认。
完整数据库、聊天消息与报告尚未验证。下文实机前的能力边界按当时状态保留，末节记录新增实测证据。
上一轮实际成果为七个原生源码／构建文件和一份记录，已审核后独立保存为 `bb48d63`。
其中构建必需的 `minhook-pins.json` 被仓库的通用 JSON 忽略规则遮蔽，已显式纳入该提交。
原有正式 QQ 修改及无关未跟踪文件保持原样；没有合并或推送。

本轮完成的是 **自建宿主 → 实际 Windows 远程载入 → 原生接收 → 私有 IPC → 既有事件解析与首页认证 → 停止及宿主卸载**。
此阶段尚未验证真实 54395；后续已验证的具体范围见末节，不外推跨机器或其他版本兼容性。

## 实现与边界

实现均位于 `scripts/spikes/qq_native_event/`，不接入正式 Echo：

| 文件 | 职责 |
| --- | --- |
| `loader.cpp` | 一个显式 PID、创建时间、完整映像路径及 SHA256；载入固定摘要的 DLL，调用其唯一会话入口；私有 IPC 与匿名管道桥接 |
| `session.h` / `session.cpp` | 固定一次性 ABI；在 DllMain 外安装、读取、停止；至多一个目标载荷；取消、断连及绝对期限；不含解码／取钥算法 |
| `connect.mjs` | 校验本机构建回执，启动自有载入器，消费限定帧，调用既有 `observeCdeResponse`；认证和停止均确认后才报告成功 |
| `approved_session.mjs` / `run_session.py` | 待单独批准的实机入口；复用现有资源版本、进程代际、模块及数据库只读检查；只用私有 stdin 传选择信息及加密前缀 |
| `host.cpp` / `session_check.mjs` / `check.py` | 复用自建宿主和现有 Windows Job；产生虚构响应、注入故障及验证停止后行为 |

沿用原来一个接收函数、精确 `wrapper.node` SHA256、函数 RVA、PE unwind 和双语义锚点准入；
没有新接收点、堆扫描、协议重放、客户端安全设置或安装目录修改。
未重新实现 Protobuf、SQLCipher、候选认证或 QQ Provider。
新代码为 Echo 自主实现；沿用固定源码摘要、源码本地编译的 BSD-2-Clause MinHook，保留其完整许可证。
没有复制或运行 QScope 的 GPL 实现。

### 载入的具体含义

实机入口先用现有 `read_qq_resources` 核对活跃资源为 `9.9.37-54395`，检查期末身份仍一致。
原生载入器再核对同一登录会话、同一用户、x64、映像路径／摘要／PID 及创建时间，
并在加载前确认唯一已加载的 `wrapper.node` 位于所选安装树内且摘要完全匹配。
组件内部再次核对模块和接收函数条件。不支持未知版本、自动改选 PID 或重复安装。

载入方式是对获批进程执行两次 `CreateRemoteThread`：
第一线程只执行系统 `LoadLibraryW`，第二线程只执行已校验 DLL 的 `EchoSessionRun`。
系统导出按实际所属系统模块及 RVA 定位，并只比较 32 字节公共代码，避免跨进程 ASLR 假设。
不申请调试特权、挂调试器、修改现有线程上下文或写入自制可执行 shellcode。
远程写入仅为 DLL 路径（上限 64 KiB）及固定会话配置；没有密钥或流量。
远程参数仅在线程确认退出后释放；超时／状态未知时保留到目标正常退出，避免释放仍被读取的参数。
失败后不会自动重试或杀 QQ，也不能保证故障载入已经完全撤销。

这仍然是 **进程内载入和 Hook**，会改变进程运行时行为，绝不是普通只读检测。
[Microsoft 的线程 API 文档](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createremotethread)
也说明此操作可能改变线程时序、内存布局并触发额外 DLL 通知，甚至引发锁相关问题。
自建宿主成功不能证明 QQ 或其防护一定允许加载。

### IPC 与停止屏障

管道名含每次随机生成的 256 位会话值；单实例、首实例独占、当前用户专用 DACL，拒绝远程客户端。
双方分别通过 Windows 的服务端／客户端 PID 查询及创建时间核对进程身份，
再逐字节校验固定会话配置。随机值用于会话绑定，不是数据库密钥。
依据：[CreateNamedPipeW](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew)、
[GetNamedPipeServerProcessId](https://learn.microsoft.com/en-us/windows/desktop/api/winbase/nf-winbase-getnamedpipeserverprocessid)。
这不声称能抵抗已控制同一用户进程或拥有系统权限的攻击者。

唯一合法交付序列为 `Ready → [Target] → Finished → EOF`。
目标载荷上限 8192 字节，整条公开给 JS 的二进制通道总量上限 8256 字节。
只检查接收事件对象的命令元数据，匹配 `OidbSvcTrpcTcp.0xcde_2` 才访问目标 vector。
其他命令载荷不读取、不转发。第一次目标捕获后槽位被消费并擦除，不可再次捕获。

最后一个已捕获载荷在停止屏障前交付；取消则丢弃未交付载荷。
**调用原生停止后不再发送载荷；只有非敏感停止状态。**
`Finished` 要求观测已停、Hook 已禁用且已统计的回调退出；JS 还要求载入器正常退出，才确认停止。
即使载荷已经在途，收到取消的载入器也会丢弃它；停止确认后任何额外帧都会拒绝整个会话。
超时按组件入口的绝对期限计，不允许安装开销顺延 120 秒的观测期限。
清理确认允许短暂宽限，但不能延长捕获窗口。

断连由原生会话循环发现并停止；如果控制器已消失，就没有可信回执，外侧仍报告停止未确认。
生产组件不调用 `FreeLibrary` 或释放 trampoline：延迟进入 detour 的线程不能仅凭瞬时 inflight=0 排除。
正常停止表示不再观测，**不表示组件完全卸载**；组件及保留资源随 QQ 正常退出释放。
只有虚构宿主导出一个专用“全部生产线程已 join”证明，允许测试组件释放资源并
使用 [FreeLibraryAndExitThread](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-freelibraryandexitthread) 完整卸载。
生产 DLL 不含这个释放入口或宿主协作机制。

载荷只在原生槽位、受限内存管道和 JS Buffer 中流转；使用后主动擦除。
密钥从不经过 Python 或远程参数，不写文件、诊断、错误文本或报告。
没有原始通信落盘、聊天解码或数据库查询。应用主动擦除不等同于对操作系统分页、崩溃转储或运行时内部副本的全局保证；本轮不更改这些系统设置。

## 实际编译与自测结果

使用现有 MSVC x64、Windows SDK、Node 和已核验的项目解释器，未安装或升级依赖。
最终构建无编译错误或警告。所有诊断／宿主子进程使用任务自有隔离用户目录。

| 场景 | 实际结果 |
| --- | --- |
| 虚构登录响应 | 实际远程加载 DLL，经私有管道交付，既有 JS 链认证首页成功；随后停止确认、完整宿主卸载 |
| 首页认证失败 | 只认证该一次候选并拒绝；正常停止、卸载、宿主继续运行 |
| 取消 | Ready 后取消，无目标交付，停止确认并卸载 |
| 超时 | 无目标响应，窗口到期停止、卸载 |
| 控制器异常退出 | 原生端自行停止，宿主证明卸载后继续运行；外侧诚实保留停止未确认 |
| 宿主异常退出 | 载入器／JS 拒绝认证结果，自有 Job 回收；不声称宿主存活或 DLL 主动卸载 |
| 错误进程创建时间 | 加载前拒绝，无 Hook；自建宿主继续运行 |

每个存活宿主在停止后继续调用 **128 次目标回调**；原生工作线程确认槽位仍空，
宿主确认原始入口恢复、组件不再加载、原始函数继续可调用。
JS 对停止后的额外字节拒绝，因此正常成功同时要求没有后续载荷。
既有适配器定向回归仍通过，包括长／短字符串、无关载荷 guard page、安装失败、
错误版本、原始异常传播、繁忙卸载拒绝及正式变体拒绝虚构宿主。
所有自有 Node／载入器／宿主进程经现有 Job 核验释放。
实机入口也保持现有 Job 的空输入合同：Job 内 Python 工作进程再建立 Node 的私有输入管道，
取消使用任务自有 Windows 事件；没有更改正式启动器或将日常 QQ 纳入 Job。

复现命令（以下只触及自建宿主；目录须新建且属于当前任务）：

```powershell
& scripts/spikes/qq_native_event/build.ps1 -BuildRoot <本工作区build下的任务目录>/native
& .venv/Scripts/python.exe scripts/spikes/qq_native_event/check.py <native目录> <新建自测目录> --session
& .venv/Scripts/python.exe scripts/spikes/qq_native_event/check.py <native目录> <新建回归目录>
```

实际脱敏回执保留于任务自有忽略构建目录：`build/qq-session-ipc-20261114/`，不提交二进制、私有路径或回执文件。
源码和此记录现纳入下一阶段开始前的独立本地提交；构建产物及本机状态回执仍留在忽略目录，不合并、不推送。

## 首次实机前方案（历史记录）

**本轮没有执行以下步骤。** 计划只允许一次主进程、一次载入会话、一个接收点、120 秒和一个 8 KiB 目标响应。

1. 由用户正常退出日常 QQ，从原官方入口启动，停在手动登录前。工具不结束、启动或自动登录 QQ，
   不添加 `--no-sandbox`、不更改自动登录配置或任何客户端保护。
2. 在用户批准范围内只核对该新主进程的代际、活跃版本与模块身份；
   必须已经加载经过验证的 `wrapper.node`，且用户尚未发起这次登录。
   如果自动登录已发生或没有这个时间窗口，停止；不声称当前载入器已解决更早的启动拦截。
3. 显式选定所授权 `nt_msg.db`，只读前 5120 字节到内存，确认包装／页大小；
   不生成真实库副本、不读聊天正文、不打开 Provider 或报告。
4. 单独批准 `run_session.py --approved-single-session` 的明确 PID、创建时间、安装路径及数据库选择；
   该入口执行上述两线程载入、一个接收 Hook 和私有 IPC。
   参数中的批准标记只是防误运行，不替代人的授权。
5. 看到 `armed` 后由用户完成普通登录。不发送消息、不主动请求或重放目标协议。
   第一个目标响应到达、无目标超时、用户 Ctrl+C、身份变化、解析／认证失败、IPC 异常，均停止一次会话。
   真实目标若内层仍加密、字段不同或数据库页发生变化，失败关闭，不尝试其他 Hook、解包猜测或候选。
6. 结束后再读同一加密前缀一次，复核前缀、资源版本和进程代际仍一致。
   整次最多读数据库 10240 字节；成功也只证明该前缀的认证与事件来源，不能外推完整库／WAL／历史聊天可用。
7. 无论认证结果如何，用户正常退出 QQ，使组件／trampoline／可能保留的参数彻底释放，
   再从普通官方入口启动即可恢复日常使用。工具没有需要还原的安装文件或客户端设置。

**是否需要退出并重新登录：本次方案需要安排一次正常重启及手动登录。**
依据是目标为登录相关 `0xcde_2` 响应，没有证据证明已登录状态必然再次产生它，
而新进程也为一次性组件和完整清理提供边界。这是实验时序要求，不是已证明所有取钥都必须重登。
若当前客户端无法在 wrapper 加载后、目标响应发生前等待手动登录，则当前方案尚不能保证捕获；
不因此自动改为调试启动、绕过保护或更广的观测。

风险包括载入被拒绝、Hook 改写入口时线程时序变化、登录失败、卡顿或进程崩溃。
身份绑定期间只读文件句柄会临时禁止所选映像／模块被替换，不应与客户端升级同时操作。
MinHook 的线程暂停能力也不构成 QQ 全线程安全保证。
遇到权限、防护、版本或模块不符就停止，不提升权限或关闭防护。
Ctrl+C 只请求停止观测；收到停止确认仍不能声称 DLL 卸载。
若没有停止确认或 QQ 无响应，按状态未知处理；不自动杀 QQ，由用户另行决定结束方式。
故障载入后不要再次注入或重建覆盖该批 DLL，应先让该 QQ 正常退出。

实机验收必须同时取得同次会话的版本／模块绑定、真实目标事件、现有字段可解析、
指定首页认证通过及停止确认；当前仅完成其自建宿主准备，等待单独实机批准。

首次实机准备复核：已重新编译并完成宿主验收，结果增加非敏感的 `event_parsed` 字段，
利用既有类型化错误区分解析拒绝与首页认证拒绝；对未知异常保留未知状态。
补充的一个畸形虚构响应验证了“捕获成功、解析失败、认证未成功”，没有新增解析实现。
本机活跃资源版本及磁盘模块摘要仍匹配，但尚未执行真实进程载入或 Hook；
用户登录只能在新会话收到 `armed`、并经操作方明确提示后开始。

## 后续获批实机实验结果

在用户逐次批准真实载入及单个接收 Hook 后，使用本机 Windows QQ **9.9.37-54395** 完成实际观测。
以下记录是此前“仅自建宿主准备”之后的新证据；没有扩大到聊天正文、全库解密或报告。

- 第一次：120 秒窗口结束，无目标事件；解析与认证未执行。登录是否落在窗口内没有时间证据。
  已确认 Hook 禁用、回调退出，随后用户正常退出 QQ；只读检查确认 QQ 与实验原生辅助进程均不再运行。
- 第二次：用户重新批准新进程的一次载入和 Hook，收到真实 `armed` 后扫码登录。
  在限定窗口内实际捕获 `OidbSvcTrpcTcp.0xcde_2`，既有解析器成功，候选通过指定数据库首页认证。
  用户登录确认回查约在会话启动后 61 秒；组件状态为 `authenticated_event`，作用域 `first_page_only`。
  实机入口结束码为 0，意味着前后加密前缀、资源版本和进程代际的既有复核也通过。
  已收到停止确认，Hook 已禁用、inflight 为 0；当时生产 DLL 仍驻留。
  随后用户正常退出 QQ；只读检查确认 QQ 与实验原生辅助进程均为零，实验作业已结束，
  组件资源已随目标进程退出释放。没有自动结束或重启日常 QQ。

第二次观测提供了此前缺失的实际证据：这个精确版本和模块身份下，受限接收位置能够交付可解析目标响应，
其候选与所选加密首页匹配。不能由此宣称所有账号、其他版本、完整数据库／WAL、消息读取或报告均已验证。
候选仅用于内存认证并已清理；没有密钥、原始响应、聊天正文、账号或私有路径落盘。
两次只保存脱敏状态回执于任务自有忽略目录，不提交二进制，不合并或推送。
