# 明确授权账号资料的离线导入：最小可行性验证

用户已确认第一版 QQ 产品改为“明确授权本地账号资料 → 离线快照 → GUI 会话分析”。
本轮承接 `4a020f1` 及当前未提交的登录观察研究，不继续寻找登录回调。
只检查现有源码并运行人工构造样本；没有查询真实 QQ、读取真实配置／账号目录／数据库、
安装 Hook、取钥或请求新实机操作。没有修改正式 Facade／GUI 或构建 Frozen／Setup。

## 结论

**退出前短暂持有凭据事件、退出后冻结输入再同步认证解密的顺序可行，但完整导入准入
尚未成立：现有捕获凭据没有可验证的账号绑定。** 暂不能把所选目录名称当作已验证的本人。
当前先要解决的是本次凭据与所选资料账号的可信关联，不是持续在线登录生命周期。
不能将这个缺口用目录名、人工确认或单次 MAC 成功补作已验证。

## 已实际执行的虚构时序

新增 `scripts/spikes/qq_offline_import_check.py`，仅接受工作区 build 下的新隔离目录，
不存在真实 QQ 模式。沿用显式虚拟环境解释器和当前工作树源码，核对目标依赖范围和 pip
一致性；未安装或升级依赖。外层 owned Job 对整个诊断及所有子进程施加 60 秒硬截止。
隔离用户目录及环境在 worker 启动前建立，不访问真实配置或注册表来获得测试结果。

1. 复用已有 SQLite 保留区样本构造器、人工表和既有测试 encoder，生成两份加密数据库。
   凭据随机生成，不写入文件、命令行或输出；取钥响应为人工构造事件，不冒充真实原生捕获。
2. Node worker 持有有界凭据事件，此时没有创建认证密钥租约。另一个自有 Python 子进程
   打开第一份源库写句柄，模拟待退出的 QQ；它不是实际 QQ 进程。
3. 生产 `snapshot.prepare` 在自有写者仍存活时拒绝；独立调用生产 `_read_locked`，
   Windows 实际共享模式也因已有写句柄而拒绝。没有放宽源锁或 sidecar 检查。
4. 只对自有虚构写者发送正常结束信号并确认退出，再对两份输入调用生产 `snapshot.prepare`。
   唯一替换的 OS 状态观察是 `assert_qq_exited`：以该虚构子进程的真实退出状态代替查询 QQ。
   ACL 保护、源读锁、源身份／大小／摘要、辅助文件拒绝、复制及后验验证均走生产实现。
5. 之后才将快照描述通过私有 stdin 交给 Node。复用生产 `observeCdeResponse`、
   `withAuthenticatedKey`、`decryptSnapshot`，在同步作用域内完成逐页认证、解密及最终化。
   Python 再核对两份输出的 SQLite `integrity_check=ok` 和人工内容。
6. 消费结束后，检查借用的原始密钥 Buffer 和转移所有权的事件 Buffer 已清零。
   错误加密页、取消、过期、消费异常及异步消费均拒绝，并检查可观察凭据缓冲区清零。
   最终清零保留的原始事件，确认自有 Job 及 helper 退出。

最终脚本完成上述流程，回执为 `exit_before_snapshot=true`、`live_writer_refused=true`、
`retained_event_authenticated_after_exit=true`、`sqlite_integrity_verified=true`、
`credential_account_binding_proven=false`、`raw_keys_persisted=false`、`real_qq_accessed=false`。
没有通过把 raw key 带出既有同步租约来等待用户操作。缓冲区检查不声称能检查 JS 引擎、
密码库或操作系统的所有内部内存副本。

这证明的是组件之间的离线编排可行性；尚未实现正式 worker 的跨退出协议，未验证真实 QQ
退出后一定没有 WAL／SHM，也不证明现有正式 GUI 已支持该顺序。若真实退出仍留下辅助文件，
现有冻结入口继续拒绝，不允许删掉源 sidecar 或把普通文件复制当成一致快照。

## 账号绑定反例与源码证据

在虚构样本中，两份库位于不同账号标签下，使用同一随机凭据、不同盐。调用方的请求账号
始终保持第一项，但认证解密器对第二项同样成功。这不是声称真实 QQ 会复用密码；它证明
现有 API 并不检查请求账号和数据库账号的关系，目录标签也不参与密码学身份认证。
复制或重命名资料目录不能因此获得已验证的本人身份。

- `qq_login_event_probe.mjs::observeCdeResponse` 解析的目标字段是响应命令及凭据材料，
  没有返回经验证的账号标识。
- `qq_key_source.mjs::withAuthenticatedKey` 的绑定是版本、profile、获取任务标签和页面摘要，
  没有账号身份。源码已明确 MAC 只证明页面／密钥相符，不能代替来源证明。
- 现役原生 `inspect_response` 只捕获目标响应 payload，不向 worker 发出账号或请求关联证明。
- 既有发送任务元数据实验独立读取过账号候选，但不是现役响应捕获的一部分；原始类型 0
  的既有证据不能自动升级为通用账号枚举，也没有建立本次请求／响应的可信关联。
- 前一次成功回调与本人 UIN 匹配是有价值的独立证据，但不能把不同实验的身份、凭据及
  数据库拼接为本次导入绑定。将来若复用一次成功声明，仍须在同一次任务内明确证明其与
  捕获凭据、授权资料的关系；这不要求恢复持续在线凭据，也不能静默忽略冲突。

因此当前不是“只剩一次 GUI 真人验收”：正式导入之前须先有可验证的账号绑定来源。
没有这样的证据，就不能将账号目录名称传给 Provider／Adapter 作为可信 `self_uin`。
本轮没有增加新 Hook 或继续逆向来寻找该来源，也没有用去掉本人校验的 GUI 掩盖缺口。

## 成果及结束边界

保留最小离线诊断脚本与本记录，正式代码没有行为改动。账号自动发现、多会话 GUI、正式
worker 跨退出编排及 Frozen／Setup 均未实施，不能报告普通用户已可通过完整 GUI 生成 QQ 报告。
具备可信单次账号绑定后，才可把已有组件接入并用虚构多账号／群聊／私聊完成 GUI 验收；
随后还需单独授权的真实 QQ 全流程验收，不能直接跳到真人操作或候选构建。

当前任务成果留在原分支等待研究审核，未提交、未修改 main、未合并、推送或发布。
自有虚构快照、明文样本、生成的 fixture 和回执留在忽略的 build 范围，待本项研究审核
收尾时按所有权规则处置；现有未跟踪资产和上一轮观察成果原位保留。
