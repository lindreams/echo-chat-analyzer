## 0. 现状取证（本设计的事实基础）

本节记录设计前对当前代码的实际验证结果。后续阶段不得基于猜测推翻这些事实，
但应在实现前用虚构数据复验。

### 0.1 当前实际链路

```text
ImportService → Analysis Scope Filter → run_smart_profile → _analyze_kept_messages → analyzer.top_words
```

关键位置：`application/analysis_service.py` 中的 `_analyze_kept_messages()`
是**词频 token 流的唯一装配点**：它逐条调用 `clean_text()` 与 `tokenize()`，
把结果累加进 `tokens` 与 `sender_tokens`，再交给 `analyzer.top_words()` 计数。

这个事实非常重要：**所有词频质量问题都可以在 token 装配阶段解决，
而不需要修改 `analyzer.py`。**

### 0.2 @消息的真实行为（与初始假设不同）

`cleaner.py` 的 `_MENTION_RE = @[^\s@，。！？、,:;；]+` 已经会删除 @ 段。
实测（虚构样本）：

| 输入 | clean_text 输出 | 结论 |
| --- | --- | --- |
| `@张三 今天晚上开黑吗` | `今天晚上开黑吗` | 被 @ 的昵称**没有**进入词频 |
| `@张三你好啊我们明天去吃饭` | 空字符串 | **正文被整条误删** |
| `@小明　收到了吗`（全角空格） | `收到了吗` | 正常 |
| `@Zhang San hello there` | `San hello there` | 含空格昵称**残留后半段** |

因此问题 1 的真实形态需要修正为三点：

1. 昵称进入普通词频只发生在**昵称含分隔符**（空格、点号等）时；
2. 无分隔符的 @ 消息会**吞掉正文**，这是数据损失，比词频污染更严重；
3. @ 关系信息在清洗阶段被**销毁**，无法用于关系分析。

### 0.3 mention 关系其实已经存在，但被投影丢弃

`rich_message.py` 已定义 `MentionRelation`，`qq_chat_exporter_adapter.py`
已从 QQ elements / mentions 中解析出 mention 与 reply 关系。
但 `legacy_projection.py` 只投影文本，`relations` 被完全丢弃；
`ImportOutcome` 也只携带 `ChatMessage`。

微信 `wechat_db_adapter.py` 目前不产出 mention 关系。

结论：QQ 侧关系数据**已在源头存在**，属于"投影损失"而非"来源缺失"。

### 0.4 模板过滤存在一处明确接线缺口（最高性价比问题）

`template_detector.py` 会产出两类候选：`welcome_template` 与
`repeated_template`。但 `decision_engine.py` 只处理 `robot_sender`、
`welcome_template`、`automation_source` 三类，`repeated_template` 落入
`else` 分支，变成：

```text
target_type="unknown", action="review", reason="unsupported_candidate_type"
```

而 `filter_pipeline.py` 的 `_decision_matches_message()` 对 `unknown`
一律返回 `False`。

实测（虚构样本，6 条签到 + 6 条欢迎 + 5 条重复笑声）：

```text
CAND repeated_template  score=1.0  "签到成功，当前积分 {number}"
DEC  unknown / review / unsupported_candidate_type   ← 永不生效
CAND welcome_template   score=1.0  "欢迎 {variable} 加入群聊"
DEC  template / ignore / high_confidence_welcome_template
结果：kept=11 filtered=6
```

即"签到成功"这类最典型的机器人模板**当前完全没有被过滤**，
检测器已经识别出来了，只是决策层没有接线。

### 0.5 停用词现状

- `stopwords.txt` / `stopwords_topic.txt` / `stopwords_culture.txt`
  分别为 163 / 163 / 162 行，内容高度重复，三个 profile 差异极小；
- 三个文件中**纯 ASCII 词条数量为 0**，即当前完全没有英文停用词；
- `tokenizer.py` 只额外丢弃单个 ASCII 字母、1–2 位整数、`3x` 类数量词和
  单个中文字符；
- 因此 `the / to / my / in / is / and` 等英文功能词**必然进入词频**。

实测：一条 22 词英文复制文本贡献了 `to / my / friends / in / China` 等全部 token。

### 0.6 权重与重复现状

- 词频按 token 出现次数累加，**每条消息权重相同且不设上限**：
  一条超长消息可以贡献几十个 token，等价于几十条正常消息；
- 当前**没有任何重复消息检测**；
- `AnalysisDiagnosticCounts` 已有 raw / imported / scope / filtered / analyzed
  五个可选计数，并随 Report Package metadata 持久化
  （原先的 `ReportHistoryManager` / `analysis_history.jsonl` 已退休），
  是"有效消息数 / 重复消息数"的天然落点。

## 1. 问题分析：为什么 stopwords 解决不了

停用词只是一个**词级别的黑名单**，它作用在链路最末端，且不携带上下文。
本次五类问题里只有一类真正属于词级别。

### 1.1 停用词的四个结构性局限

1. **粒度错位。** 污染源是"消息"，惩罚对象是"词"。
   一条超长复制文本的问题不是"`friends` 是坏词"，而是"这一条消息不该拥有
   几十倍权重"。把词拉黑会在所有正常消息里同时失去这个词。
2. **语义误伤。** 模板消息里的词往往是正常汉语高频词。
   把`欢迎 / 加入 / 成功 / 查询 / 积分`拉黑后，真人说"欢迎回来""查询一下"
   也会消失，且无法恢复。
3. **不可解释、不可撤销。** 停用词表是扁平文本，没有理由、类别和置信度。
   用户看到词云缺词时无法知道是哪一层规则删的，也无法只撤销某一条。
4. **无法产出关系与统计。** @谁、重复多少条、有效消息多少条，
   这些是**结果**，停用词只会让证据消失，不会产生指标。

### 1.2 五类问题的正确归属层级

| 问题 | 污染层级 | 正确处置层 | 停用词能否解决 |
| --- | --- | --- | --- |
| @消息 | 消息结构 | 结构解析 + 关系提取 | 否，且会误删正文 |
| 超长复制文本 | 消息权重 | 消息分类 + 权重 | 否 |
| 英文功能词 | 词 | 分层停用词 | **是**（唯一适合的一类） |
| 机器人 / 模板 | 发送者 / 整条消息 | 三层过滤（已有骨架） | 否 |
| 重复消息 | 消息集合 | 去重统计 + 权重 | 否 |

结论：真正缺的不是更长的停用词表，而是**在 token 之前对"消息"做出判断，
并让判断结果可解释、可撤销、可统计**。

## 2. 推荐架构

### 2.1 结论

**需要新增一个中间层，但只需要一个，并且放在应用层内、Analyzer 之前。**

推荐引入三个概念，全部位于新目录 `src/qq_chat_analyzer/quality/`：

| 概念 | 职责 | 是否 P0 |
| --- | --- | --- |
| `MessageQualitySignal` | 一条消息的**只读质量标注**（不改消息本身） | 是 |
| `MessageClassifier` | 由消息集合产出分类与 signal，不做过滤 | 是 |
| `MessageQualityAnalyzer` | 聚合 signal 产出质量统计（有效/重复/降权计数） | P1 |

**不新增** `MessageMetadata`。理由：它与 `MessageQualitySignal` 职责重叠，
且"metadata"这个名字会诱导后续开发者把任意字段挂上去，
最终变成第二个扁平能力集合——这正是 `ECHO_ARCHITECTURE_DECISION.md`
判定 `ChatMessage` 不该走的路。

### 2.2 层次位置

```text
ChatMessage（不变）
    ↓
Analysis Scope Filter（不变）
    ↓
Smart Filter / run_smart_profile（扩展，不重写）
    ↓
【新增】Message Quality Layer
     ├─ MessageClassifier      → 分类 + MessageQualitySignal
     └─ MessageQualityAnalyzer → 质量统计（P1）
    ↓
Token 装配（_analyze_kept_messages，扩展）
    ↓
Analyzer 核心（零改动）
    ↓
Presentation / Dashboard（P2 才触及）
```

### 2.3 为什么放在应用层而不是 analysis/

三条硬约束决定了位置：

1. `ARCHITECTURE.md` 第 8 节不变量规定 `analysis/` 不得 import
   `application`，且 Analyzer"不负责过滤策略"。
   质量判断**是**价值过滤策略，因此不属于 Analysis Core。
2. 质量判断需要**跨消息统计**（模板频次、重复率、长度分布），
   而现有 analyzer 是逐报告独立函数，塞进去会破坏其纯粹性。
3. 现有 Smart Filter（`detectors/` + `decision_engine` + `filter_pipeline`）
   已经是"应用层之前的价值判断层"，且已在 `analysis_service.py` 中被调用。
   质量层与它同级、同风格，是**最小认知负担**的位置。

### 2.4 与现有 Smart Filter 的关系

不新建平行体系。现有三段式 `Candidate → FilterDecision → FilterPipeline`
被**复用并扩展**：

```text
detectors/  ──→ Candidate ──→ decision_engine ──→ FilterDecision ──→ FilterPipeline
                                                                          ↓
                                                    kept_messages + 【新增】signals
```

关键区分：

- **FilterPipeline 负责"删"**（action=ignore，整条移出）；
- **Quality Layer 负责"标"**（不删，只附加 signal 与权重）。

这一区分直接回应任务要求"不要简单提出删除长消息"：
长文本走"标 + 降权"路径，模板与机器人走"删"路径。

### 2.5 signal 的传递方式（关键设计决策）

`MessageQualitySignal` **不挂在 `ChatMessage` 上**，而是作为**旁路集合**传递：

```text
QualityAssessment(
    signals: Mapping[消息索引 or message_id, MessageQualitySignal],
    counts: QualityCounts,
)
```

索引键优先使用 `message_id`；`message_id` 为 `None` 或重复时降级为
消息在 kept 列表中的位置下标。该降级必须显式记录，不得静默假设 ID 唯一
（`ECHO_ARCHITECTURE_DECISION.md` 未决问题 3 明确 ID 稳定范围尚未验证）。

旁路传递的收益：`ChatMessage` 零改动，`analysis/` 零改动，
且质量层可以随时整体移除而不留下字段残骸。

## 3. 是否修改 ChatMessage

### 3.1 结论：不修改

`ChatMessage` 是 `frozen=True, slots=True` 的冻结契约，
`ARCHITECTURE.md` 4.3 明确"新增展示需求不通过扩展它来满足"，
`ECHO_ARCHITECTURE_DECISION.md` 2.3 明确"新能力不得以给 ChatMessage
继续加 Rich 字段作为默认方案"。

本设计的全部五个功能**都不需要**修改它：

| 功能 | 所需信息 | 来源 |
| --- | --- | --- |
| @处理 | mention 关系 | 已存在于 `RichMessage.relations`（QQ）；或从文本二次提取 |
| 长文本 | 文本长度、字符构成 | `ChatMessage.text` 已足够 |
| 英文停用词 | 无 | 停用词文件 + tokenizer 调用方 |
| 模板检测 | 文本 + 发送者 | 已足够 |
| 重复检测 | 文本 + 发送者 | 已足够 |

### 3.2 唯一需要扩展的边界：mention 的传递通道

QQ mention 关系存在于 `RichMessage`，但 `ImportOutcome` 只携带
`ChatMessage`。若要做真正的关系分析（P1），需要一条通道。

**最小方案（推荐）**：扩展 `ImportOutcome`，新增一个可选字段
携带 `RichMessage` 序列或"消息键 → mention 目标"的轻量映射。

```text
ImportOutcome(
    result, processed_message_count, messages,
    + rich_messages: tuple[RichMessage, ...] = ()   # 可选，缺省为空
)
```

理由：

- `ImportOutcome` 是**应用层内部**结构（其 docstring 已写明 "Internal"），
  不是冻结跨层契约，扩展成本低；
- 默认空元组，所有现有调用方与测试不受影响；
- 符合"Raw → Rich → Legacy Projection 单向"约束，不做 Legacy → Rich 回填；
- 不需要修改 `ChatMessage`、任何 adapter 的转换语义或 parser 输出。

**P0 不做这一步。** P0 的 @处理只需修正 `cleaner` 的正文损失问题
（见 5.1），关系分析留到 P1 再打开这条通道。

### 3.3 明确不采用的方案

- ❌ 给 `ChatMessage` 加 `mentions` / `quality_score` / `is_duplicate` 字段；
- ❌ 用 `dataclasses.replace` 生成"清洗后的 ChatMessage"替换原消息
  （会让原始事实与派生结果混淆，违反 3.3 事实与派生分离原则）；
- ❌ 在 `ChatMessage` 上加 `metadata: dict`（等于放弃类型约束）。

## 4. 新分析链路设计

### 4.1 目标链路

```text
ChatMessage 序列
        ↓
[1] Scope Filter                      （现状，不改）
        ↓
[2] Smart Filter                      （扩展决策接线）
     发送者过滤 / 模板过滤 → 整条移出
        ↓
[3] Message Classification            （新增）
     ├─ normal_text     普通聊天正文
     ├─ mention_heavy   以 @ 为主体
     ├─ long_form       超长文本（可能是正常长讨论）
     ├─ pasted_content  复制 / 营销 / 外部文本
     ├─ template_like   模板残留
     └─ duplicate       完全或高相似重复
        ↓
[4] Quality Signal 生成               （新增）
     每条消息 → 分类 + 权重 + 理由 + 置信度
        ↓
[5] Token 装配（加权）                （扩展 _analyze_kept_messages）
     ├─ 正文分析      ← 权重生效
     ├─ 关系分析      ← mentions（P1）
     ├─ 模板分析      ← 模板统计（P1）
     └─ 噪声分析      ← 质量计数（P1）
        ↓
[6] Analyzer 核心                     （零改动）
        ↓
[7] Dashboard                         （P2 才展示质量指标）
```

### 4.2 四路分析的分工

任务要求的"普通文本分析 / 关系分析 / 模板分析 / 噪声分析"四路，
映射到实际产出：

| 路径 | 输入 | 产出 | 阶段 |
| --- | --- | --- | --- |
| 普通文本分析 | normal_text + long_form（降权） | 加权 token 流 → 现有词频/词云 | P0 |
| 关系分析 | mention 关系 | 谁@谁、互动对数 | P1 |
| 模板分析 | template_like 候选 | 模板列表 + 命中条数 | P1 |
| 噪声分析 | 全部 signal | 有效/重复/降权/过滤计数 | P0（计数）/ P2（展示） |

### 4.3 权重如何生效（不改 analyzer 的关键）

`analyzer.top_words()` 接收 `list[str]` 并用 `Counter` 计数。
权重通过**在装配阶段控制 token 进入次数**实现，而不是修改计数逻辑：

- 权重 `1.0`：token 全部进入（现状行为）；
- 权重 `0.0`：该消息 token 不进入词频（但消息仍计入活跃度等报告）；
- 权重 `0 < w < 1`：采用**确定性截断**，而非随机抽样。

确定性截断规则（必须可复现，禁止随机）：
对该消息的 token 序列去重后保留每个**唯一 token 一次**
（即"一条消息内同一词只投一票"），必要时再对 token 总数设上限。

这个规则同时解决了两个问题，且不引入浮点抽样的不确定性：

- 超长复制文本从"贡献 22 个 token"降为"贡献 N 个唯一 token 且各计一次"；
- 重复刷屏消息不再线性放大词频。

**重要**：权重只影响**词频/词云链路**（`tokens`、`sender_tokens`）。
`ActivityAnalyzer`、`MessageLengthAnalyzer`、`ConversationAnalyzer`
继续接收未降权的 `kept_messages`，因为"用户确实发了这条消息"是事实，
不应因质量判断而在活跃度里消失。这条边界必须在实现阶段用测试锁定。

## 5. 功能设计

### 5.1 @消息处理

**输入**：`ChatMessage.text`；P1 追加 `RichMessage.relations` 中的
`MentionRelation`。

**输出**：
- 正文文本（移除 @ 段后的真实内容）；
- mention 目标列表（P1）；
- 分类 `mention_heavy`（当移除 @ 后正文为空或过短）。

**判断方式**：

P0 首要任务是**修正现有正文损失**，而非新增功能。当前
`_MENTION_RE = @[^\s@，。！？、,:;；]+` 是贪婪的"吃到分隔符为止"，
导致两类错误：

1. `@张三你好啊我们明天去吃饭` → 整条被删（无分隔符，全部吃掉）；
2. `@Zhang San hello` → 昵称含空格，只删掉 `@Zhang`，`San` 残留成词。

改进方向（按可靠性排序）：

1. **已知参与者名单匹配（推荐）**：mention 的目标几乎总是会话内的发送者。
   用当前会话的 sender 集合构造匹配集，优先做**最长匹配**。
   这与 `interactive_bot_detector.py` 的 `_compile_mention_pattern()`
   已有做法完全一致——**该能力已存在，只是未被 cleaner 复用**。
2. **结构化 mention（QQ，P1）**：直接用 adapter 已解析的
   `MentionRelation.display_text` 精确定位并剥离。
3. **保守回退**：无法匹配已知名单时，只剥离 `@` 到**首个空白**，
   且**若剥离后正文为空则保留原文**，宁可残留一个昵称也不丢正文。

`@全体成员` 保持现有整体移除行为。

**影响**：
- 修复正文丢失（真实数据质量提升，非纯粹清洗改进）；
- 昵称不再残段进入词频；
- 为 P1 关系分析保留 mention 目标；
- **风险**：`cleaner.py` 属于 Analyzer 核心范围，本轮范围明确"不修改 Analyzer 核心"。
  因此见 6.4 的处理方式：**@ 剥离改进需要单独提出并获得人工批准**，
  或将改进实现为质量层的独立预处理步骤而非改写 `cleaner.py`。

---

### 5.2 长文本 / 复制文本处理

**输入**：`ChatMessage.text`、该次分析的长度分布、发送者上下文。

**输出**：分类（`long_form` 或 `pasted_content`）+ 权重 + 理由。

**判断方式**：绝对阈值不可靠（不同群聊差异极大），采用**相对分布 + 多信号**。

第一步，相对长度定位：
- 用本次分析集合的长度分位数（如 P95 / P99）而非硬编码字符数；
- 仅"长"不构成降权理由，只是进入进一步判断的门槛。

第二步，区分"正常长讨论"与"复制文本"（这是本功能的核心）：

| 信号 | 倾向复制/营销 | 倾向正常长讨论 |
| --- | --- | --- |
| 语言构成 | 与会话主体语言不同（中文群里的整段英文） | 与会话主体语言一致 |
| 词汇重复度 | 低（成篇文章，类型-形符比高） | 中（口语重复多） |
| 换行 / 排版 | 多换行、项目符号、大量标点 | 少 |
| 上下文连续性 | 孤立出现，前后无关联 | 处于该发送者的连续对话中 |
| 跨发送者重复 | 同一段文本多人发过 | 唯一 |
| URL / 联系方式 | 常含 | 少含 |
| 发送者行为 | 该发送者仅此一条超长 | 该发送者常写长消息 |

**要求至少两个独立信号同时成立**才判定 `pasted_content`，
与 `robot_detector.py` 现有 `len(reasons) < 2` 门槛保持一致。

第三步，处置——**降权，不删除**：

| 判定 | 处置 |
| --- | --- |
| `long_form`（正常长讨论） | 权重保持，或仅施加"一条消息内同词一票" |
| `pasted_content`（高置信） | 权重降至"唯一 token 各一次"，且计入噪声统计 |
| 不确定 | 保持原权重，记录 signal 供人工复核 |

**明确不做**：不按长度阈值删除消息；不因超长而将消息从活跃度统计中移除。

**影响**：
- 单条超长英文文本不再垄断高频词；
- 正常长讨论者（认真写长文的人）不被惩罚；
- `China / friends / Trump` 这类**主题词**在正常消息中出现时依然保留
  ——因为处置对象是"消息权重"而不是"词"。

### 5.3 英文停用词

**设计原则**：

1. **分层而非合并。** 停用词从单文件升级为**分层来源**，每层可独立启用/禁用：

```text
第 1 层  中文常用词      现有 stopwords*.txt（不改内容）
第 2 层  英文功能词      新增，仅限封闭类功能词
第 3 层  平台噪声词      新增，如图片/表情/系统占位残留
第 4 层  群自定义词      用户级，可覆盖与撤销
```

2. **英文层只收封闭类功能词。** 允许收录：冠词、介词、代词、连词、
   助动词、系动词、常见缩写（`the / a / an / to / in / of / my / your /
   is / are / was / and / but / it / this / that / with / for`）。

3. **严禁收录开放类实词。** 名词、动词、形容词、专有名词
   （`China / friends / Trump / Thursday / crazy`）**一律不进停用词**。
   这是不可协商的红线，因为它们可能正是会话主题。

4. **大小写归一但不改变原词形。** 匹配时不区分大小写；
   词频展示保留原始形态（现有 tokenizer 已保留 `Hello`、`China` 原形）。

5. **可解释。** 每层有明确类别标签，用户看到"某词被过滤"时能知道层级来源。

**分类方式**：按"是否可能成为聊天主题"划分，而非按词频高低。
判据是**封闭类词性**（closed-class）：语言中数量固定、不新增成员的词类，
天然不承载话题信息。这个判据可机械检查，不依赖主观感受。

**实施要点**：
- 新增独立文件（如 `stopwords_en_function.txt`），
  **不修改**现有三个中文停用词文件的内容；
- `tokenizer.py` 的 `_load_stopwords()` 当前只接受**单个路径**。
  分层加载应在**调用方**（`analysis_service.py` 装配阶段或质量层）完成合并，
  或由 Facade 传入已合并的临时词表路径——**避免修改 tokenizer 签名**，
  从而不触碰 Analyzer 核心。
- 现有三个 profile 差异极小（163/163/162 行且内容重复），
  分层机制天然为将来真正区分 profile 留出空间，但本轮不重排 profile 语义。

### 5.4 模板消息检测

**设计原则**：

1. **P0 的第一件事是修 bug，不是加功能。**
   见 0.4：`repeated_template` 候选已被检测出来，但 `decision_engine.py`
   未处理该类型，导致决策为 `target_type="unknown"` 而永不生效。
   接线此一处即可让"签到成功""查询结果"类模板真正被过滤。
   这是本设计**收益/成本比最高**的单项。

2. **过滤整条模板，不拆词。** 严格遵守 `AGENTS.md` 的三层过滤原则：
   模板层删整条消息，不把`欢迎 / 加入 / 成功`放进停用词。

3. **保守优于激进。** 模板过滤会删除整条消息，误伤代价高，
   因此高置信才 `ignore`，否则 `review`。

4. **可解释、可撤销。** 每个决策已携带 `confidence` / `reason` / `source`
   （`FilterDecision` 现有字段已满足），P2 可让用户覆盖。

**规则来源**（按优先级）：

| 来源 | 说明 | 状态 |
| --- | --- | --- |
| 统计自动发现 | `template_detector` 的指纹归一 + 频次聚类 | 已实现，需接线 |
| 结构特征 | 占位符数量、静态字符长度、发送者集中度 | 已在 metadata 中，未被决策使用 |
| 发送者关联 | 模板集中于单一发送者 → 提升置信 | metadata 已有 `top_sender_ratio` |
| 用户自定义 | 用户手动标记模板 | P2 |
| 内置常见模板 | **不采用**——会变成规则平台，且难以覆盖各群差异 | 明确不做 |

**决策接线建议**（供实现阶段参考，阈值需用虚构数据校准）：

`repeated_template` 应映射为 `target_type="template"`，
并结合已有 metadata 决定 action：
- 命中条数足够 + 静态字符足够长 + 发送者高度集中 → `ignore`；
- 否则 → `review`（保留但记录）。

必须避免的误伤：`repeated_template` 的指纹只要含一个数字就会成立
（`_FINGERPRINT_PATTERN` 匹配任意数字），
因此`我8点到`这类真人消息也可能形成模板组。
这正是为什么**不能**简单把所有 `repeated_template` 设为 `ignore`，
必须叠加静态长度与发送者集中度门槛。

**影响**：机器人模板从词频与消息计数中移除，且移除有据可查。

### 5.5 重复消息检测

**设计原则**：

1. **重复不等于删除。** 重复消息是**真实发生的行为**
   （刷屏、复读、附和都是有意义的社交信号）。
   处置方式是**降权 + 计数**，不是移出。
2. **区分两种重复**，处置不同：

| 类型 | 判断 | 处置 |
| --- | --- | --- |
| 完全重复 | 归一化文本完全相同 | 同一发送者连续复读 → 词频降权；计入重复计数 |
| 高相似重复 | 归一化后差异极小 | 仅标注 + 计数，不降权（P1） |
| 跨发送者相同长文本 | 同一段长文本多人发送 | 强化 `pasted_content` 判定 |

3. **相似度算法保持简单。** P1 使用可解释的轻量方法
   （归一化后的字符集合重叠或长度归一编辑距离），
   **不引入** embedding、向量库或聚类框架。
4. **复读容忍（2026-09-16 修正）。**
   原判断「`哈哈哈哈哈哈` 这类表达不需要特殊规则，避免过度工程」
   已被真实用户结果推翻。

   当前真实结果：

   - `哈哈` 与 `哈哈哈` 会作为**两个不同的 lexical token** 进入统计；
   - 从用户感知上，它们通常属于**同一类笑声表达**；
   - 因此需要后续**独立设计**：repeated-laughter lexical normalization。

   定位：

   - 属于 analysis quality backlog；
   - **不是 Release Blocker**；
   - 本次只记录设计问题，不实现算法。

   明确约束：

   - **不做「所有连续重复字符压缩」。**
     `好好` / `看看` / `慢慢` 等重复字符可能具有真实语言意义，
     统一压缩会造成误伤；
   - 当前**不提前决定**：
     regex、canonical length、similarity threshold、dictionary、clustering；
   - 未来单独设计、RED、real-data acceptance，再决定实现形态。

**统计方式**：复用已有的 `AnalysisDiagnosticCounts`，
它已具备五个可选计数并已持久化，扩展成本极低：

```text
原始消息数    raw_message_count        （已有）
导入消息数    imported_message_count   （已有）
范围内消息数  scope_message_count      （已有）
过滤后消息数  filtered_message_count   （已有）
分析消息数    analyzed_message_count   （已有）
+ 有效消息数  effective_message_count  （新增，权重 > 0）
+ 重复消息数  duplicate_message_count  （新增）
+ 降权消息数  downweighted_message_count（新增）
```

三个新计数均为**可选、默认 None**，与现有字段风格一致。
诊断 / 来源元数据现由 Report Package metadata 承载
（原先的独立 JSONL 历史 `ReportHistoryManager` / `analysis_history.jsonl` 已退休，
演进边界见 `ARCHITECTURE.md`）。

**隐私约束**：计数只保存数字。重复消息的**正文绝不进入**历史记录、
日志或 metadata——这与现有诊断元数据的隐私要求完全一致。

## 6. 优先级

排序依据：**收益 / 复杂度 / 对 MVP 的影响**。
原则是先修已确认的缺陷，再加新能力；先不可见的正确性，再可见的界面。

### 6.1 P0（高收益 / 低复杂度 / 不动核心）

| # | 项目 | 收益 | 复杂度 | 触及范围 |
| --- | --- | --- | --- | --- |
| P0-1 | 接线 `repeated_template` 决策 | 高（签到/查询类模板立即被过滤） | 很低 | `decision_engine.py` |
| P0-2 | 英文功能词分层停用词 | 高（英文噪声词立即消失） | 很低 | 新增词表 + 装配处合并 |
| P0-3 | 质量层骨架 + 消息分类 + signal | 中（为后续全部功能奠基） | 中 | 新增 `quality/` |
| P0-4 | 加权 token 装配（同词一票 / 上限） | 高（超长文本不再垄断词频） | 中 | `analysis_service.py` 装配处 |
| P0-5 | 有效/重复/降权计数 | 中（用户可解释性） | 低 | `dto.py` + `report_history.py` |

P0 的共同特征：**不修改 `analyzer.py` / `tokenizer.py` / `cleaner.py` /
`analysis/` / `ChatMessage` / GUI / Provider**。

P0-1 与 P0-2 可以作为**第一个独立小阶段**先行交付，
两者都不依赖质量层，且立即产生可感知的质量提升。

### 6.2 P1（明确价值 / 中等复杂度）

| # | 项目 | 说明 |
| --- | --- | --- |
| P1-1 | 复制/营销文本多信号判定 | 语言构成、重复度、跨发送者重复 |
| P1-2 | mention 关系通道 | 扩展 `ImportOutcome` 携带 rich 语义 |
| P1-3 | 关系分析（谁@谁） | 新增独立 analyzer，遵循 `ARCHITECTURE.md` 7.2 |
| P1-4 | 高相似重复检测 | 轻量相似度，不引入向量库 |
| P1-5 | 模板分析报告 | 展示命中的模板与条数 |
| P1-6 | `MessageQualityAnalyzer` | 聚合 signal 产出质量报告模型 |

### 6.3 P2（依赖前序 / 或触及 GUI）

| # | 项目 | 说明 |
| --- | --- | --- |
| P2-1 | Dashboard 展示质量指标 | 需改 GUI，本轮明确排除 |
| P2-2 | 用户覆盖与撤销界面 | 三层过滤的人工干预入口 |
| P2-3 | 群自定义停用词管理 | 用户级词表 |
| P2-4 | @ 剥离改进（见 6.4） | 需人工批准是否动 `cleaner.py` |
| P2-5 | 群关系网络 / 互动分析 | 依赖 P1-3 |

### 6.4 需要人工决策的一个冲突点（重要）

本轮范围规定"不修改 Analyzer 核心"，而 `cleaner.py` 属于 Analyzer 核心
（`ARCHITECTURE.md` 4.5 明确 `cleaner.py` 为 v1 核心，
7.1 明确"不许修改 `cleaner.py`"）。

但 0.2 取证显示 `cleaner.py` 的 @ 正则存在**真实数据损失缺陷**
（`@张三你好啊我们明天去吃饭` → 空）。这不是质量优化，是 bug。

三个可选方向，**由人工决定，本设计不擅自选择**：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A（推荐） | 作为独立 bugfix 小阶段修 `cleaner.py` 的 @ 正则，单独批准 | 触碰核心，但范围极小且有测试保护 |
| B | 在质量层做 @ 预处理，`cleaner` 不动 | 出现两处 @ 处理逻辑，违反"不复制逻辑" |
| C | 暂不处理，P2 再议 | 正文丢失持续存在 |

设计倾向 **A**：因为 B 会造成职责重复，而这是 `AGENTS.md` 明确禁止的。
但 A 必须作为**单独提出、单独批准**的阶段，不能混进质量层实现。

## 7. 明确暂不做

以下内容在本设计范围之外，后续阶段**不得**以"顺手实现"为理由引入：

**架构与模型**
- 不修改 Analyzer 核心：`analyzer.py`、`tokenizer.py`、`analysis/`；
  `cleaner.py` 仅在 6.4 方案 A 获批后才可单独触碰；
- 不重构或扩展 `ChatMessage`；
- 不实现完整 Rich Semantic Model 迁移（那是独立的架构阶段）；
- 不引入 `MessageMetadata` 这类开放式字段容器；
- 不修改 Provider、Adapter、Parser 的转换语义；
- 不改变 Snapshot 结构或 Snapshot 兼容规则。

**算法与依赖**
- 不引入云端 AI、在线 API 或任何网络调用；
- 不引入本地大模型、embedding、向量数据库；
- 不做机器学习分类器训练（无标注数据，不可解释，不可复现）；
- 不引入聚类框架、规则引擎框架或工作流框架；
- 不使用随机抽样做降权（必须确定性可复现）。

**产品与界面**
- 不修改 GUI 与 Dashboard（质量指标展示留到 P2）；
- 不建设"大型规则平台"或可视化规则编辑器；
- 不做跨会话/跨平台身份合并；
- 不做情绪分析、话题建模、摘要生成。

**过滤策略**
- 不按长度阈值直接删除长消息；
- 不把模板词、主题词加入停用词；
- 不删除重复消息（只降权 + 计数）；
- 不让质量判断影响活跃度、消息长度、会话概览等非词频报告。

**隐私**
- 不把聊天正文写入历史记录、日志、metadata 或测试 fixture；
- 测试只使用虚构数据（`AGENTS.md` 强制要求）。

# 11. 设计修正（最终定稿）

> **本节优先于前文。** 第 4–6 节中与本节冲突的部分以本节为准，
> 特别是 4.3（权重生效方式）、5.1（@处理定位）、5.2（长文本处置）
> 与 6.1（P0 范围）。前文保留作为分析过程与长期方向记录，
> 但**实施依据是本节**。

## 11.1 当前产品阶段目标（判断一切取舍的准绳）

当前目标**不是**建设完整的聊天研究系统，**不是**追求分析深度或指标数量。

当前目标是：

> **让普通用户获得可信、可解释的聊天分析结果。**

由此导出三条判定规则，后续阶段遇到取舍时直接引用：

1. **可解释优先于精确。** 一个用户能理解的粗糙规则，胜过一个说不清的精巧规则。
2. **修复优先于新增。** 已确认的错误行为（误删正文、失效的模板过滤、
   缺失的英文停用词）比任何新能力更值得先做。
3. **沉默的行为是缺陷。** 如果系统悄悄改变了结果而用户无法得知原因，
   即使结果"更好"，也算质量问题而非质量改进。

第 3 条直接决定了 11.3 关于权重的修正。

## 11.2 修正一：@消息问题重新定位

### 原设计的错误定位

前文（尤其 5.1）把 @消息问题与"关系分析需求"并列陈述，
容易被理解为"@处理是为了做谁@谁"。**这个定位是错的。**

### 修正后的定位

@消息问题的本质是**现有清洗逻辑的误伤缺陷**，是数据正确性问题，
不是分析能力缺口。

**P0 只做两件事，都是修 bug：**

| # | 缺陷 | 现象（0.2 实测） | 修复目标 |
| --- | --- | --- | --- |
| 1 | @ 后正文被吞掉 | `@张三你好啊我们明天去吃饭` → 空字符串 | 正文必须完整保留 |
| 2 | 昵称残留进入正文 | `@Zhang San hello there` → `San hello there` | `San` 不得成为词频 token |

修复原则：

- **宁可残留一个昵称，也绝不丢失正文。**
  剥离后若正文为空，则回退保留原文。
- 优先用**会话内已知发送者名单做最长匹配**来确定 @ 的边界
  （该能力已存在于 `interactive_bot_detector.py`，属于复用而非新建）。
- 无法匹配名单时，采用保守回退：只剥离到首个空白，且执行上一条空正文回退。

### mention 关系提取：明确降级

**mention 关系提取不属于第一阶段目标。** 具体地：

- ❌ P0 不提取 mention 目标；
- ❌ P0 不扩展 `ImportOutcome` 携带 `RichMessage`（前文 3.2 的通道**不在本轮打开**）；
- ❌ P0 不做"谁经常@谁"、群关系网络、互动分析；
- ✅ 3.2 记录的最小通道方案**仅作为未来可选路径保留**，需独立阶段与独立批准。

理由：关系分析是新增能力，而正文丢失是正在发生的数据损失。
按 11.1 规则 2，后者先做。

---

## 11.3 修正二：不在第一阶段改变 Analyzer 输入权重

### 保留的长期方向

第 4.3 节描述的"确定性截断 / 同词一票 / token 上限"作为
**长期设计方向依然有效**，不予废弃。

### 第一阶段的明确修正

**第一阶段不修改进入 Analyzer 的 token 权重。** 即：

- ❌ 不做加权 token 装配（原 P0-4 从 P0 移除）；
- ❌ 不因质量判断让任何消息的 token 减少或消失；
- ✅ 词频/词云链路在第一阶段的输出**与当前行为保持一致**。

### 为什么

核心理由是**可解释性**，即 11.1 规则 3：

如果先上线降权，用户会遇到一个无法理解的现象——
"我明明记得群里聊过这个词，为什么词云里没有？"
而此时系统**没有任何界面**能告诉他"这条消息被判定为复制文本、已降权"。
这会直接损害"可信"这一当前阶段的核心目标。

正确顺序是：

```text
第 1 步  质量标记（标了但不生效，用户无感）
   ↓
第 2 步  可解释统计（用户能看到"有多少条被标记"）
   ↓
第 3 步  展示（用户能看到"哪些被标记、为什么"）
   ↓
第 4 步  才考虑让权重真正影响词频
```

**先让用户看懂，再让系统动手。** 在第 3 步完成前，不允许进入第 4 步。

### 第一阶段质量层的角色

质量层在第一阶段是**纯旁路观察者**：

| 允许 | 禁止 |
| --- | --- |
| 生成 `MessageQualitySignal` | 修改消息 |
| 产出可解释统计计数 | 影响 token 流 |
| 记录分类、理由、置信度 | 影响任何现有报告 |

验收标准非常明确：**接入质量层前后，全部分析输出逐字节等价。**
这条可以用测试机械验证，是第一阶段质量层唯一的硬性验收条件。

## 11.4 修正三：拆分为两个独立部分（不做一次大型重构）

原第 6 节把五项功能混在 P0/P1/P2 三档里，容易被读成一次连续改造。
**现明确拆为两个彼此独立、可分别验收的部分。**

### 第一部分：已有问题修复（Existing Defect Fixes）

**性质**：修复已确认的错误行为。不新增分析能力，不新增用户可见功能。

| # | 项目 | 缺陷依据 | 触及范围 | 复杂度 |
| --- | --- | --- | --- | --- |
| A-1 | 模板检测已有能力未正确生效 | 0.4 实测：`repeated_template` → `unknown` → 永不生效 | `decision_engine.py` | 很低 |
| A-2 | 英文功能词污染 | 0.5 实测：三份停用词表 ASCII 词条为 0 | 新增词表 + 调用方合并 | 很低 |
| A-3 | @清洗误伤 | 0.2 实测：正文被吞 / 昵称残留 | 见 11.5（需批准） | 低 |

第一部分的共同特征：

- 每项都有**实测证据**支撑，不是主观改进；
- 每项都能**独立交付**，互相之间无依赖，可任意顺序或并行；
- 每项都有**明确的正确/错误判据**，容易写测试；
- 全部不引入新概念、新目录、新数据结构。

**A-1 与 A-2 是整个方案中收益/成本比最高的两项**，建议最先做。

### 第二部分：未来能力（Future Capabilities）

**性质**：新增分析能力。需要新概念与新数据结构。

| # | 项目 | 依赖 |
| --- | --- | --- |
| B-1 | 质量标记骨架（`quality/` + signal，纯旁路） | 无 |
| B-2 | 重复消息检测（完全重复优先） | B-1 |
| B-3 | 长文本 / 复制文本识别（多信号判定） | B-1 |
| B-4 | 噪声统计与可解释计数 | B-1 |
| B-5 | 质量指标展示（GUI） | B-4；**本轮明确排除** |
| B-6 | 消息质量评分影响词频权重 | B-5 完成后才可评估 |
| B-7 | mention 关系提取与关系分析 | 独立批准 |

**关键约束**：

- 第二部分**不得**在第一部分完成前启动；
- B-1 到 B-4 全程保持"标记但不生效"，输出等价性必须可测试证明；
- **B-6 不在本设计授权范围内**，它需要 B-5 落地后重新评估并单独批准。

### 两部分的边界纪律

```text
第一部分：让现有逻辑正确工作      ← 不新增概念
        ↓ （完成并验收后）
第二部分：让系统理解消息质量      ← 新增概念，但先不生效
```

禁止把两部分合并成一次改造。禁止在做第一部分时"顺手"引入 `quality/` 目录。

## 11.5 `cleaner.py` 修改授权（唯一待批准的阻塞项）

A-3（@清洗修复）需要触碰 `cleaner.py`，而它属于 Analyzer 核心
（`ARCHITECTURE.md` 4.5、7.1 明确列为不许修改）。

本节修正前文 6.4 的表述，明确立场：

**A-3 是缺陷修复，不是质量增强。** 因此推荐 **方案 A**：
作为一个范围极小的独立 bugfix 阶段修改 `cleaner.py` 的 @ 正则，
并用虚构数据测试锁定行为。

排除方案 B（在质量层做 @ 预处理）的理由已更充分：
既然第一阶段质量层是纯旁路、不允许改变文本，
在质量层做 @ 剥离会与该定位直接矛盾，还会造成两处 @ 逻辑。

**这是本设计中唯一需要人工批准才能启动的条目。**
在获得批准前，A-1 与 A-2 可以照常推进，两者不依赖 A-3。

## 11.6 架构约束（再次确认，适用于全部阶段）

以下约束在第一部分与第二部分**全程有效**，不因阶段推进而放宽：

1. **不修改 `ChatMessage`。** 冻结契约保持；质量信号走旁路传递，
   不挂字段、不加 `metadata` 字典、不用 `replace` 生成替身消息。
2. **不重写 Analyzer。** `analyzer.py`、`tokenizer.py`、`analysis/` 不改；
   `cleaner.py` 仅在 11.5 获批后以最小范围触碰。
3. **不破坏 QQ / 微信统一模型。** Provider、Adapter、Parser 的转换语义不变；
   统一进入 `ChatMessage` 的现状不变；不新增平台分支。
4. **不引入大型框架。** 无云端 AI、无本地大模型、无 embedding、
   无向量库、无机器学习分类、无规则引擎、无工作流框架。
   不使用随机抽样（一切判定必须确定性可复现）。
5. **小阶段推进。** 每阶段独立可验收，遵循
   设计 → RED 测试 → 实现 → GREEN 测试 → 完整 `pytest` → `git diff --check`。
   禁止把多个条目合并成一次提交。
6. **隐私不变。** 聊天正文不进入历史记录、日志、metadata 与测试 fixture；
   测试只使用虚构数据。
