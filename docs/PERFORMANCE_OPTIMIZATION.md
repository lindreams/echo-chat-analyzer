# 大规模数据优化记录

基线：`203ed0a8231517e98d0e0cdb223fce89aca2677a`。本轮仅做局部优化，
不改变统计、QQ 身份、快照准入、媒体完整性或单在途合同。

## 1. Direct DB payload 只写出一次

原实现：SQLite → records → JSON 写盘 → 清理快照 → 元数据请求 →
JSON 全量读回 → 补充身份 → JSON 再写盘。现在在 provider 中共用
`read_session_payload` 构造原始数据，Direct DB 服务在清理快照后原位补充身份，
只写最终 JSON。现有文件导入接口和独立 materialize 接口保持不变。
原始 records 不复制；服务在交给 ImportService 前释放 payload 引用。

### 本机合成对照（2026-11-09）

Windows x64，Core i9-14900HX，15.7 GiB 物理内存，Python 3.13.9，
SQLite 使用该解释器自带版本。每次使用新 Python 进程，串行运行 3 次。
自动化 HOME、USERPROFILE、APPDATA、LOCALAPPDATA 均隔离。

局限：这里不包含真实 QQ 登录、快照捕获/解密、核心统计、媒体恢复或报告导出；

## 历史验收边界

此前真实约 57.6 万条：148 秒、核心约 76 秒；约 11.1 万条：50.5 秒，
并有图片 58 → 53 的待核验回归；Frozen 媒体软预算 45 秒、第一群仍有
344 项未完成。朋友曾等待近 10 分钟、素材目标 1,525 项。
这些均为历史测量，本轮没有真实 QQ 数据重测，收益和完成率仍未知。
此前 347 MiB / 100 万条合成数据库的指定场景 48 → 11 秒也保持为历史证据，
不能与上面的全会话 payload 测量或真实全流程混算。

产品的普通群多数 30 秒、大群 30–60 秒、极端群尽量 3 分钟以内及无数秒 GUI
卡顿目标，尚不能据本轮合成对照宣告达成。报告生成、素材恢复和任务墙钟时间
必须在真实验收中分别记录。
