# Echo 统一数据模型概念设计

> **基线导航（2026-10-07）**：本文保留历史概念设计，不作为当前实现合同。
> QCE resources 等来源描述属于已退休的审计基线；现役统一模型与 QQ Direct DB / WeChat
> 边界见 [ARCHITECTURE](../ARCHITECTURE.md)，不据此恢复旧文件兼容。
> 下文 Dashboard 为历史设计用语；旧 Qt 页面及专属数据构建链已退休，现役展示使用 Echo Report。

## 1. 目的与范围

本文定义 Echo 未来统一数据模型的概念边界。它不设计 Python class、数据库表、
字段类型、序列化格式或迁移代码，也不改变当前架构事实。

设计目标是让来源层可以把 QQ 和微信中已经确认的丰富数据转换成来源无关的 Echo
语义，使 Analysis 能逐步理解：

- 谁参与了交流；
- 何时发生；
- 说了什么或分享了什么；
- 对谁、对哪条消息作出回应；
- 发生了哪些行为和状态变化；
- 关系与群体如何随时间变化。

统一模型不是 Raw Source 的镜像。它只接纳当前有明确价值或具有明显分析发展空间
的概念。平台专有 payload、未验证字段和弱相关资料留在来源边界之外。

## 2. 现状约束

当前 `ChatMessage` 是文本导向、冻结的跨层契约，包含时间、发送者、消息类型、文本、
来源、若干 ID 及 system/recalled 标志。现有 Analysis Core 主要消费 timestamp、sender
和 text；message ID、稳定 sender ID、conversation ID 和 recall 状态尚未形成关系或
事件分析。

Raw Source Audit 同时证明当前统一契约无法无损表达已经存在的核心语义：

- QQ 消息可由多个 element 组成，同一条消息能同时包含文本、图片、@ 和回复；
- 微信引用依靠 `refermsg/svrid` 指向另一条消息，不只是一个 `reply` 类型标签；
- QQ 与微信都有图片、表情、文件、语音、视频及资源关联；
- recall 既是消息当前状态，也可能是含操作者和目标消息的事件；
- join、leave、poke 和系统交互不是普通用户文本消息；
- nickname、group nickname 和 role 具有不同作用域，不能折叠成一个 sender 字符串。

因此本设计保持 `Raw Source → Provider → Adapter → 统一语义 → Analysis` 的方向，
但把“统一语义”从单一文本消息概念提升为若干彼此有清晰边界的概念。

## 3. 设计原则

### 3.1 核心与扩展分层

每条消息都需要稳定的 Message Core；内容、关系、事件和身份上下文按实际存在组合。
缺少图片 OCR 或语音转写不应阻止消息进入 Echo。

### 3.2 语义归一，而非字段汇总

统一层表达“回复目标”“提及对象”“资源引用”等跨来源含义，不直接暴露
`replyElement`、`refermsg`、`local_type` 等来源字段。来源原始类型可以作为可追溯信息，
但不能要求 Analysis 理解平台编码。

### 3.3 事实与派生结果分离

消息类型、目标 ID、资源元数据属于来源事实；OCR、转写、视觉描述、情绪标签、机器人
判断属于后续派生结果。派生失败不能改变原始事实，也不能让一条语音消息消失。

### 3.4 消息、关系、事件、身份分离

四类概念生命周期不同：消息描述通信载体，关系连接实体，事件描述状态变化，身份描述
参与者及其上下文。把它们都塞进 text 或 message type 会导致语义冲突和重复。

### 3.5 渐进兼容

当前文本分析已经可用，未来模型不能要求所有 Analyzer 同时升级。旧分析路径可以继续
消费文本投影；新能力逐步消费更丰富的统一语义。

## 4. 概念全景

```text
Conversation Context
  ├─ Participants / Identities
  ├─ Messages
  │    ├─ Message Core
  │    ├─ Content Parts
  │    └─ Relations
  └─ Events
       └─ may affect Message, Identity, or Conversation state
```

这不是实现对象图，只用于说明概念归属：

- Message Core 确认一条通信记录的身份和位置；
- Content 表达它承载了什么；
- Relations 表达它与其他消息或参与者如何连接；
- Events 表达聊天空间中发生的动作或状态变化；
- Identity 为上述概念提供稳定参与者及上下文名称。

## 5. Message Core

### 5.1 职责

Message Core 描述“一条来源内可识别的消息记录”。它只包含跨来源都成立的基础语义：

- 消息身份：能够在来源或会话范围内稳定引用该消息；
- 来源：来自哪个聊天平台或导入来源，用于追溯而非平台分支分析；
- 会话：消息属于哪个私聊、群聊或其他会话上下文；
- 发送者：指向稳定 Identity，而不是只保存当时的展示名；
- 时间与顺序：恢复消息在会话中的位置；
- 消息类型：描述文本、图片、混合内容等规范化类别；
- 可见性/状态：例如是否已撤回，但不代替完整 Recall Event。

### 5.2 边界

Message Core 不保存：

- 具体文本或资源文件；这些属于 Content；
- 被回复消息或被提及用户；这些属于 Relations；
- 入群、退群等群体变化；这些属于 Events；
- 昵称、群名片和角色的全部细节；这些属于 Identity Context；
- OCR、转写、主题等分析结果；这些属于派生能力。

### 5.3 ID 语义

QQ 已确认 id/msgId，微信已确认 `server_id` 与 `local_id`。Echo 需要“可被其他关系引用的
消息身份”，但本阶段不决定选用哪一个字段、如何组合或使用何种类型。设计上必须承认：

- 来源可能同时提供服务器 ID 与本地 ID；
- reply 或 recall 可能只携带其中一种；
- ID 的稳定范围可能是平台、账号、会话或某次导入；
- 统一层需要保留足够的来源上下文以避免不同来源 ID 碰撞。

## 6. Content

### 6.1 Content 是可组合的

消息内容不能再假定为单个 text。QQ 原始消息已经证明一条消息可以同时包含多个
elements；微信 AppMsg 也可能携带标题、引用与资源。Echo 概念上应允许一条消息具有
一个或多个有顺序的 Content Part。

“可组合”是语义要求，不代表本阶段决定具体容器或字段类型。

### 6.2 Text

Text 表示发送者实际输入或来源明确给出的可读正文。它是当前 Analysis 的主要输入。

边界：

- 引用的旧正文不是当前消息 Text，而是 Reply 关系的可选引用摘要；
- 系统生成的可读文案属于 Event 或 System Content，不冒充用户输入；
- OCR、语音转写是派生文本，必须保留其派生来源，不能覆盖原始 Text。

### 6.3 Image

Image 表示图片内容及其可用元数据/资源引用。当前最小价值是消息存在、数量、发送者与
时间；未来可承载 OCR、视觉描述、相似图片和 AI 记忆。

核心不要求保存图片二进制，也不要求来源必须能恢复本地文件。资源缺失时，图片消息
仍然成立。

### 6.4 Emoji / Sticker

Emoji/Sticker 表示平台内置表情、商城表情或自定义动画表情。应保留能稳定区分表情的
标识及可用资源引用，同时把“文本 Unicode emoji”和“平台贴图/表情资源”视为可以不同
表达的内容。

未来分析包括表情使用习惯、回应方式和情绪辅助信号；它不应在接入时被直接解释为固定
情绪。

### 6.5 File

File 表示一次文件分享及文件名、大小、格式等可用元数据。文件正文不默认进入核心，
也不要求 Echo 自动打开或索引文件。

未来可以按用户授权增加文档理解，但“分享过某文件”是独立且先行成立的聊天事实。

### 6.6 Voice

Voice 表示语音消息、时长及资源引用。转写是可选派生结果，不是 Voice 成立条件。

这一边界允许当前先进行语音数量、时长和时序分析，未来再增加本地转写、语义检索和
AI 记忆，同时保持隐私约束。

### 6.7 Video

Video 表示视频消息、时长、尺寸或缩略图等可用元数据及资源引用。视频理解、关键帧、
OCR 和语音识别属于未来派生能力。

### 6.8 资源引用

Content 与本地/远端资源之间需要“可定位但不保证可用”的概念关系，因为 Audit 已确认：

- QCE `resources` 可以提供类型、文件名和大小；
- 微信资源可能位于 image、video、voice、file、attach 等不同位置；
- 某些资源只能依据 ID、MD5、时间或目录启发式匹配；
- CDN URL 可能过期，文件也可能已被清理。

因此资源可用性必须与消息事实分开：资源不可访问不能删除消息，也不能改变其类型。

## 7. Relations

### 7.1 为什么独立于 Content

关系描述“实体之间的连接”，内容描述“消息承载了什么”。二者独立的原因是：

- 一条含图片的消息仍可回复另一条消息；
- 一条文本可同时 @ 多人；
- Reply 即使只有目标 ID、没有引用摘要，关系仍然成立；
- 同一条消息可以同时具有 Reply 与 Mention；
- Forward 可能连接一条来源消息或一组嵌套记录，但不改变当前消息自己的内容组成。

如果把 reply/mention/forward 只做成 message type，同一消息的多种语义会互相覆盖；
如果写进 text，Analysis 将无法可靠区分用户正文与结构关系。

### 7.2 Reply

Reply 连接当前消息和被回复消息。它可以带来源提供的引用摘要、原发送者显示名等辅助
信息，但目标消息 ID 是关系恢复的首要事实。

微信 `refermsg/svrid` 已证明可连接到原消息 `server_id`；QQ reply element 已确认包含
目标消息 ID。若目标消息未导入、已删除或超出时间范围，关系应保留为未解析引用，
而不是被丢弃。

### 7.3 Mention

Mention 连接当前消息和一个或多个 Identity，也可表示全体成员等会话范围目标。
显示文本如“@某某”只是呈现，不是稳定身份。

来源只能提供可读文本、不能可靠提供目标 ID 时，应明确标为未解析 mention，不能凭昵称
强行合并身份。

### 7.4 Forward

Forward 表示信息从其他消息或上下文被分享过来。第一阶段需要保留“发生了转发”、
可用来源关系和摘要；不要求立即把任意深度的嵌套转发全部展开到核心。

完整转发树的价值和复杂度较高，可作为后续专门能力，不阻碍基础 Forward 关系进入 P1。

## 8. Events

### 8.1 Event 的职责

Event 表示聊天空间中的动作或状态变化，而不是普通消息内容。它至少在概念上具有发生
时间、来源、所属会话、事件类别，以及可用的操作者、目标或受影响对象。

本设计不规定事件字段集合；不同事件只表达其已验证事实。

### 8.2 Recall

Recall 同时涉及两个层面：

- Message State：已知某消息目前被撤回；
- Recall Event：在某时刻由某个操作者撤回某条消息。

QQ 导出已有 recalled 状态，OneBot 运行态能提供 operator/target message；微信已确认
type 10002/revokemsg，但撤回原消息 ID 标签仍需验证。统一概念必须允许只有状态、只有
事件或二者同时存在，不能伪造缺失信息。

### 8.3 Join / Leave

Join 和 Leave 改变会话成员集合。Kick 是 Leave 的一种具有操作者的来源事实；是否进一步
细分应由已验证语义决定。

这些事件为活跃成员基数、成员留存和群体变化分析提供时间边界。运行态 OneBot notice
与历史导出能力必须区分，不能把实时可见误当作旧历史可恢复。

### 8.4 System Interaction

System Interaction 覆盖 poke/拍一拍、群管理提示及其他系统生成互动。来源若能可靠解释
事件，应转为明确 Event；若只能恢复可读文案，则保留为未细分系统事件及摘要。

系统事件不应直接进入用户词频，因为文字由平台模板生成，而不是用户自然表达。

### 8.5 Event 与 Message 的关系

某些平台把事件保存为“系统消息行”。统一模型不应继承这种存储偶然性：

- 有通信内容且需要出现在消息时间线中的记录可保留 Message 表达；
- 能明确解释为状态变化的部分表达为 Event；
- 同一来源记录可以同时提供可读时间线摘要和结构化事件，但分析时不得重复计数。

具体去重规则属于未来实现设计，本阶段只固化这一语义边界。

## 9. Identity

### 9.1 稳定身份

Identity 表示来源内可稳定识别的参与者。QQ 的 uid/uin、微信的 wxid/Name2Id 映射均说明
稳定身份与展示名不同。

稳定身份用于：

- 合并同一成员改名前后的消息；
- 连接 Mention、Event 操作者和群成员；
- 避免同名用户被错误合并；
- 支撑未来关系图和参与生命周期。

本阶段不设计跨平台真人合并。QQ 与微信身份即使显示名相同，也不能自动认为是同一人。

### 9.2 Display Name 与 Aliases

Display Name 是面向用户的当前呈现；Aliases 表示来源中已确认的 nickname、remark、alias
等可选名称。名称可能变化，也可能只在某个会话成立。

Analysis 应以稳定身份聚合，以显示名输出；没有稳定 ID 的旧导出可以降级使用来源可用
身份，但必须承认其不确定性。

### 9.3 Group Nickname

Group Nickname/群名片属于“Identity 在 Conversation 中的呈现”，不是用户永久名称。
QQ 已确认 group card 能力；微信专属群昵称字段仍需进一步验证，因此概念存在，但只能
接纳来源已证实的数据。

### 9.4 Roles

Role 表示用户在某个会话、某段时间内的 owner/admin/member 等位置。它不是全局身份属性，
也不能从发言量推断。

QQ runtime 已确认 owner/admin/member；微信已确认群主，管理员尚未确认。缺失角色应保持
未知，不默认 member。

### 9.5 Group Membership

Group Membership 连接 Identity 与 Conversation，可由成员快照或 Join/Leave 事件提供。
它不应复制到每条 Message。

快照回答“读取时有哪些成员”，事件回答“何时发生变化”，二者不可互相完全替代：
只有当前快照不能精确重建历史成员状态，只有不完整事件也不能保证得到全量成员集合。

## 10. P0/P1/P2 模型边界

### P0：首个 Rich 语义闭环必须表达

- Message Core：source、conversation、sender、timestamp、message identity、message type；
- Text Content；
- Reply Relation；
- Mention Relation；
- Recall 状态及有证据时的 Recall Event。

P0 的目标不是立刻新增统计，而是停止丢失聊天理解的基本连接。

### P1：模型应预留并逐步接纳

- Emoji/Sticker Content；
- Image、File、Voice、Video 的元数据与资源引用；
- Forward Relation；
- Group Membership、group nickname 与 role；
- Join、Leave、System Interaction 等 Events。

P1 只要求明确概念与来源事实，不要求 OCR、转写、视觉分析、完整群体算法同时完成。

### P2：暂不进入核心

- 在线状态、QQ 等级、年龄、头像挂件等弱相关或瞬时资料；
- 完整地理坐标与财务细节等高敏感内容；
- 未验证的好友关系、微信群管理员字段、微信撤回目标 ID；
- 完整来源 payload、原始数据库行和二进制资源正文；
- 自动跨平台身份合并；
- 任意深度的完整转发树。

P2 信息可在来源层继续存在，但没有验证和明确 Echo 价值前不进入核心契约。

## 11. 当前 ChatMessage 的处理选项

### 方案 A：继续扩展 ChatMessage

做法概念：继续在当前冻结消息上增加内容、关系、事件和身份字段。

优点：

- 表面迁移路径短，现有 Analyzer 仍接收同一入口；
- 少量新增 P0 字段时易理解；
- 不需要立即引入新的模型名称。

缺点：

- 当前模型以单个 `text` 和 `message_type` 为中心，难以自然表达复合内容；
- Reply、Mention、Forward、Event 和 Identity Context 会被挤进同一个扁平对象；
- 字段持续可选化，容易演变成来源字段合集；
- 与 `ARCHITECTURE.md` 将 ChatMessage 视为冻结契约的现状冲突；
- join/leave 等非消息事件被迫伪装成消息。

判断：不适合作为 Rich 能力的长期方案，只适合极小范围、经单独批准的兼容增强。

### 方案 B：升级为新的 Rich Message Model

做法概念：建立能表达 Message Core、Content Parts 和 Relations 的新统一语义，同时以
Events 与 Identity Context 补充消息之外的聊天事实。

优点：

- 概念与 Raw Audit 已确认能力匹配；
- 支持复合消息和独立关系，不让平台字段进入 Analysis；
- 可以让新分析能力直接消费结构化事实；
- 为 OCR、转写、视觉理解和关系图留出明确而有限的扩展位置。

缺点：

- 需要设计迁移边界、兼容投影和版本策略；
- Provider/Adapter/Application/Analysis 的接线将来需要分阶段调整；
- 如果一次性替换现有契约，回归风险高。

判断：是长期目标，但不应解释为一次性替换全部现有分析链路。

### 方案 C：ChatMessage 作为旧分析层模型保留

做法概念：把当前 ChatMessage 定位为“文本分析投影”，Rich 统一语义在进入旧 Analyzer
前可产生兼容的 ChatMessage 视图。

优点：

- 保持现有词频、活跃度、画像和 Dashboard 行为稳定；
- 新模型可以按概念边界演进，不受单文本字段限制；
- 支持新旧 Analyzer 并行迁移，符合产品优先和渐进兼容原则；
- 无需让旧分析器认识图片、事件或平台细节。

缺点：

- 过渡期存在 Rich 语义与旧文本投影两种模型；
- 必须明确哪一个是未来事实来源，避免双向转换和两套业务逻辑；
- 文本投影可能无法呈现所有非文本和事件信息，旧报告需承认其能力边界。

判断：最安全的迁移策略，但它必须与方案 B 配套，而不是形成长期并列的两个事实模型。

## 12. 推荐方向

推荐 **B + C 的渐进路线**：

1. 长期以新的 Rich 统一语义作为来源无关的聊天事实模型；
2. 当前 ChatMessage 保留为旧文本 Analysis 的兼容投影；
3. 新能力直接消费 Rich 语义，旧 Analyzer 继续消费 ChatMessage；
4. 数据流保持单向：Raw Source 转换为 Rich 语义，再按需要生成旧文本投影；
5. 禁止旧 ChatMessage 反向补全 Rich 数据，也禁止 Provider 同时维护两套业务转换；
6. 当旧 Analyzer 全部具备明确替代方案后，再单独决定 ChatMessage 的最终生命周期。

推荐理由：方案 A 无法承载事件和复合内容；直接只选 B 会把一次设计升级变成高风险全量
迁移；B + C 同时满足长期语义完整性与当前产品稳定性。

这是一项需要进一步人工确认的架构演进，因为当前 `ARCHITECTURE.md` 明确规定
ChatMessage 是唯一跨层模型并视为冻结契约。Phase 9.2 只记录推荐方向，不修改该架构事实。
任何实施前都必须先更新架构决策、迁移计划和兼容边界。

## 13. 与当前架构的兼容要求

未来若批准 Rich 模型，仍需维持以下不变量：

- Provider 不依赖统一模型，也不做分析或价值过滤；
- Adapter/Parser 是来源格式进入统一语义的唯一转换边界；
- Application 负责选择 Rich 分析或旧文本投影，不把转换散落到 GUI；
- Analysis 只消费来源无关语义，不出现平台条件分支；
- Presentation 不重新计算统计；
- GUI 只通过 Facade 获取结果；
- 真实正文、身份和资源不出本机，不进入日志或测试 fixture；
- 未验证字段保持未知，不因“通常存在”而创建语义。

## 14. 需要进一步讨论的架构问题

以下问题已经由本设计暴露，但不在本阶段决定：

1. **唯一跨层模型规则如何演进。** 是将 Rich 语义整体作为新的唯一事实模型，还是允许
   一段有明确期限的双模型过渡。
2. **Event 的入口。** 历史导出事件和 OneBot 运行态事件具有不同完整性，未来如何统一
   导入、去重和标记证据范围。
3. **消息 ID 的稳定范围。** QQ id、微信 server/local ID 在来源、账号、会话和导入批次
   中的唯一性需要验证后才能制定统一引用规则。
4. **身份与名称历史。** 当前展示名称由调用方注入；未来稳定 Identity、会话范围群名片
   和时间变化如何与该机制衔接。
5. **资源生命周期。** 本地文件缺失、CDN 失效、启发式匹配与用户授权应如何表达，避免
   Analysis 把资源不可用误判为消息不存在。
6. **派生内容归属。** OCR、语音转写、视觉描述应如何标注来源、版本和失败状态，同时
   不污染原始事实。
7. **系统消息双重表达。** 同一来源记录同时形成可读时间线摘要和结构化 Event 时，如何
   防止统计重复。

这些问题需要独立架构决策和实施计划。本文件不授权修改 ChatMessage、Provider、Adapter、
数据库读取或 Analysis。

## 15. GUI 连接状态不进入数据模型

连接页的“未连接 / 连接中 / 数据读取中 / READY”是 GUI 对 Facade 状态的展示映射，
不是聊天事实，也不是 Message、Relation、Event 或 Identity。数据源切换时清理的会话
列表、提示文字、搜索条件和引导图片均为临时界面状态，不写入 `ChatMessage` 或未来
Rich Semantic Model。

因此本次连接体验调整不增加任何数据字段，不改变 QQ/微信身份语义，也不授权保存登录
状态、权限提示或外部客户端生命周期信息。
